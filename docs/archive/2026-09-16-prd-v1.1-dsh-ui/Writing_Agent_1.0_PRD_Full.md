### PRD 1.1 · 2026-09-16 · CR-001：直接复用 DSH 前端 UI

**目标产品仍为 Writing Agent 1.0。本次 1.1 是文档修订号，不是宣布产品 1.1 已发布。**

#### 变更原因与已确认方向

用户明确不接受把旧桌面包 0.1.0 作为新版界面利旧方案，希望直接利用 DSH 的前端源码、页面和界面体系，并便于后续调整。该前端来源决定已确定，不再作为等待确认的可选项。

原仓库身份、历史、旧文章、风格、写作方法、核查规则与用户数据仍保留。新产品仍是源码级复用后自主维护的系统，不变成 DSH 的插件、SDK 包装或依赖其服务的客户端。

#### 与初稿不同的内容

| 初稿路线，已失效 | PRD 1.1 路线 |

| UI 调整没有独立验收 | 增加来源映射、视觉基线、主题/Slot 扩展、协议重连和独立品牌/端点验收 |

### 1. 背景与讨论结论

#### 1.1 用户要解决的问题

现有产品承担两项任务：帮助用户完成可控写作；证明并传播一套有价值的开源写作方法。下一阶段希望减少安装与使用负担，提升技术自主性，同时延续原仓库的 star、历史、样本和社区关系。

用户的核心意图不是“换一个宿主跑原有 skills”，而是“借鉴 DSH 已实现的运行时能力，把 Writing Agent 本身变成一个类似 harness 的独立 agent 系统”。产品仍专注写作，不转成通用 coding agent。

#### 1.2 保留的讨论结论

- 保留原仓库和产品名称；在新分支开发，成熟后作为原项目的大版本升级。
- 复用已有写作方法、真实素材规则、事实门禁、风格资产、版本记录和评测，不因其载体是提示词或 Python 脚本就全部重写。
- 借鉴 DSH 的模型调用、工具执行、会话事件、生命周期和扩展接口；稿件、证据、作者决定、修改与核查由 Writing Agent 自己定义。
- 直接复用 DSH 前端源码及必要依赖闭包。先保留其现有视觉和交互，再通过主题、插槽和独立写作面板扩展，避免让维护者承担从零设计 UI 的工作。
- 保留旧桌面用户数据不等于保留旧桌面界面；0.1.0 页面、样式、Tauri 启动路径不进入新产品关键路径。
- 将关键规则提升为程序契约：模型负责创作与建议，程序负责状态、权限、版本一致性和交付门禁。
- 优先完成可以运行、停止、恢复、修改、验证的最小闭环，随后扩展，不先建设插件市场。
- 传播必须展示真实可用性和差异，不把代码重构、agent 数量或 star 数当作写作质量证据。

#### 1.3 明确撤回或不采用的讨论路径

早期讨论中“以 DSH SDK/profile 为底座”“把写作做成 DSH 插件”的建议不适用，本 PRD 明确排除。初稿中复用旧 0.1.0 桌面页面和已有 Tauri 壳的路线亦已撤回；不得把 DSH 的 UI 源码复用降级为截图模仿或零散组件参考。另起独立 GitHub 仓库、整体覆盖 main、先完成通用 runtime 平台再做写作，均不是当前方案。

“Writing-visible means recoverable”是本次讨论提出的设计口号，不是 DSH 官方术语。其可测试定义是：**已确认并成功提交、会影响写作结果的状态，可以在重启后从本地记录恢复。**它不承诺恢复未提交的流式文字、模型内部推理，或让再次生成得到完全相同的文章。

#### 1.4 当前已确认基线

根包版本为 0.11.0，桌面包版本为 0.1.0；桌面路径已有 React/Tauri、阶段数据结构和 Claude Agent SDK 执行入口。现行 `claude-runtime/` 是旧工作流的唯一源，并已包含正文/标题/证据快照及事实门禁。具体 SHA 与文件见 [S02]–[S05]。

仓库元数据快照为 417 stars、63 forks、4 个 Watch 订阅者，Discussions 尚未启用。该快照不是活跃用户统计。star 本身不产生更新订阅，传播必须另有入口。[S01][S11]

本次没有运行完整测试或安装应用；所有“现有”描述以读取的文档和代码为边界。M0 必须补充代码现状和实际测试结果。

### 2. 产品定位与成功定义

#### 2.1 一句话定位

**Writing Agent 是一个本地优先、独立运行、能够围绕素材、稿件版本、证据与作者意图持续工作的开源写作 Agent 系统。**

对作者强调“能用、能改、能继续”；对开发者强调“自有 runtime、明确领域契约、可测试与可扩展”。两种表达指向同一产品，不建立两套实现。

#### 2.2 首批目标用户

第一类是愿意提供真实素材、需要写中文观点文/解释文章/经验复盘的个人作者。第二类是现有 Writing Agent 使用者，希望保留资产但降低运行环境依赖。开发者是早期协作者，不是第一版独立 SDK 的承诺对象。

默认首个完整演示覆盖“有材料的中文解释或经验文章”，目标约 1,500–3,000 字，只作为测试场景而非产品字数限制。不把长篇小说、学术论文、自动营销矩阵同时列为首发验收。

#### 2.3 产品价值假设

| 假设 | 验证方式 | 失败后的处理 |
|---|---|---|
| 独立分发能减少环境阻塞 | 干净 Windows 环境 + 5 名目标用户上手观察 | 先修安装、连接诊断与引导，不加角色 |
| 版本化修改比整篇重生更可控 | 同一草稿定向修改、锁定段落与回退任务 | 缩小修改粒度或改进冲突处理 |
| 状态与事件记录能降低中断损失 | 自动注入中断、重启、重复请求等故障 | 不发布恢复承诺，先完成恢复测试 |
| 多阶段策略有实际质量价值 | 同模型、同材料的新旧流程及简单基线盲评 | 减少无收益环节，不通过更多循环掩盖 |
| 原社区能帮助验证新版 | 自愿预览报名、真实问题、第二篇创作 | 调整定位与触达，不购买/诱导 star |

#### 2.4 非目标

1.0 不做多人协作、云账户/计费体系、自动对外发布、任意远程执行、公开插件商店、与所有 DSH 插件兼容、通用 coding agent、自动经营内容账号。语音/PDF/OCR、多平台精细排版、复杂作者记忆学习、图数据库可视化、跨版本智能合并放到后续。

不承诺完全离线 AI：应用本地运行不意味着云端模型或检索无需联网。不承诺零错误写作或任意模型可用。

### 3. 独立 runtime 的产品与技术边界

#### 3.1 必须满足的“独立”标准

**IND-01** 用户不需要安装或登录 DSH，不读取 `~/.dsh` 作为运行前提，不执行 `dsh` 启动命令。

**IND-02** 新产品的启动、会话、循环、工具调度和数据格式由原 Writing Agent 仓库的源码及构建产物负责。运行时不导入外部发布的 DSH SDK/core 包来承担这些职责，也不把 Claude Agent SDK 作为新引擎。

**IND-03** 允许按许可把 DSH 源文件及必要依赖闭包移入本仓库后适配；移入源码属于 Writing Agent 的维护范围，保留清晰上游来源。普通开源库如 Cordis、SQLite 驱动、React 或模型 HTTP 客户端可使用，须说明用途、固定版本并审查许可。

**IND-04** 打包产物经依赖、进程与文件访问测试，确认无 DSH/Claude Code 宿主依赖。仅把包名改掉但仍调用宿主不算通过。

**IND-05** 不主张移植代码为全部原创；许可证与来源说明随源码及发行包一起交付。[S10]

#### 3.2 默认实现路线

选择“依赖闭包明确的源码模块移植 + 必要的写作领域重构”。不是不经分析地复制整个仓库，也不是为了纯原创从零复写所有通用能力。

M0 对每个候选模块记录：原路径、commit、必要依赖、上游测试、拟保留接口、目标路径、许可、删除/适配内容、验证方法。DSH 的插件与服务之间存在关系，必须按最小可测试模块组处理，而非随意复制单文件。[S09]

| DSH 参考模块 | 默认动作 | 首版不带入的部分 |
|---|---|---|
| session 与相关事件/上下文投影 | 评估复用类型与投影逻辑，适配自有数据存储 | 上游全部历史格式迁移链 |
| agent / agent-loop | 移植最小运行闭环和可验证生命周期 | 完整通用调度平台 |
| llm 接口与一个适配路径 | 统一流式、工具调用、取消和错误语义 | 不经测试的全部 provider |
| tools / scope / policy | 复用或适配注册、参数校验、权限及执行记录 | 默认开放任意 shell/任意进程 |
| system-prompt/context | 复用请求组装思想，绑定内容快照 | 依赖外部配置层的完整产品组合 |
| Web UI 基础与页面 | **必须源码级移植**：布局、侧栏、会话/输入、主题、基础组件、设置、必要的客户端模型与通信闭包 | 旧 0.1.0 页面混入；默认重设计；未经审查的官方品牌、遥测、账户、更新与插件分发入口 |
| Web Host / gateway / client modules | 保留所移植前端实际依赖的启动、构建、类型生成和通信模块；在本仓库适配自有服务 | 为保留 UI 而运行外部 DSH 服务；只换 URL 不处理协议语义 |
| Desktop 源码 | 桌面交付默认优先评估 DSH Electron 源码的最小壳及匹配资产分发，另立 ADR | 复用旧 Tauri 壳作为默认；照搬上游 updater、账号、插件安装及发布基础设施 |

DSH 上游升级只通过单独 PR 审查。初始移植不应伴随所有依赖升级和全仓格式化，避免无法辨别来源与行为变化。

### 4. 产品形态与分发策略

#### 4.1 默认顺序

**M0 固定 DSH 前后端源码基线并拆出依赖闭包；M1 同步推进“自主 runtime + CLI”与“DSH 原版 UI 的本地移植基线”；M2 接通真实写作服务并增量加入稿件功能；M3 分发同源前端与自有 runtime，完成 Windows 自包含安装包。**

DSH UI 移植是首要工程工作，不等待后端全部完成才开始。M1 的 UI 可先使用明确标记的本地 mock 建立移植验收，但 Alpha 对外宣称可写作必须已接入真实运行链；mock 不等于功能完成。

本地 Web 不是云 SaaS。新客户端沿用 DSH 的 React/布局/主题/Slot 思路，必要的 client model、remote 类型和 host 通信代码由本仓库拥有。桌面与 Web 共享这一个前端和相同领域语义，不把旧 0.1.0 页面接回来。

桌面容器是独立技术选择：默认优先审计并源码移植 DSH Electron 最小壳，替换上游运行时启动、应用 ID、数据路径和更新配置；这不表示照搬 DSH 所有分发基础设施。[S17] M0 可依据构建、包体、安全与维护成本提出不同容器 ADR，经维护者批准后采用，但不能因此退回旧 UI，也不同时维护 Electron/Tauri 两套新壳。

#### 4.2 安装与启动承诺

| 阶段 | 用户承诺 | 不能宣称 |
|---|---|---|
| Alpha | 开发者可按已验证命令启动；明确需要 Node 与构建步骤 | 普通用户零配置 |
| Beta 本地 Web | 在已列出的 Node 版本下用已发布/验证的命令启动 | 没发布的 npm 包已可 npx 运行 |
| 1.0 Windows | 安装包带匹配 runtime，无需用户自行装 Node、Python、Rust、DSH 或 Claude Code | 无 Key、无额度也能调用收费云模型 |

目标命令名称为 `writing-agent web / run / inspect / resume / doctor`，均是待实现接口。npm 包名、命令是否冲突及发布权由 M0 检查；当前根包 `private: true`，不能直接把示例 npx 命令放进正式 README。[S02]

默认本地服务只监听 loopback，禁用公网绑定。非必要不需要账户注册，不上传文章遥测。首次启动引导模型连接、工作目录和数据传输说明。

### 5. 核心用户旅程

#### J1：首次写作

安装/启动 → 选择可用 provider 并安全填写 Key → 测试模型能力 → 输入主题与材料 → 显示简报、暂定方向和缺口 → 必要时确认 → 系统自主推进 → 草稿出现 → 局部修改 → 核查 → 正式导出。

目标不是尽量少问问题，而是只问改变方向、作者真实性或授权的问题。已有授权不重复问，非关键缺口可以明确暂定。没有资料时，不伪造作者亲历或虚构搜索成功。

#### J2：中断继续

运行时出现连接问题或进程退出 → 重启 → 显示最近已提交稿件、已确认决定、任务状态与未结算操作 → 用户点击继续 → 从安全边界继续。不得把整篇重新生成伪装成恢复。

#### J3：定向改稿

用户选中段落，要求改语气但不改事实 → 系统生成相对于指定版本的 patch → 差异预览 → 接受后创建新版本 → 程序使依赖旧正文的核查失效。若用户先手动改过正文，旧 patch 被拒绝并说明冲突，不静默覆盖。

#### J4：旧项目进入新版

用户选择旧目录或数据库 → 只读扫描 → 显示将导入的文章、素材、风格和不能恢复的历史 → 建立备份/独立目标 → 导入为新项目 → 保留旧文件 → 需要交付时重新核查。导入旧稿不捏造旧会话与修改链。

#### J5：发现问题并反馈

用户查看错误原因、重试边界与诊断信息 → 选择导出脱敏诊断包 → 预览会包含哪些字段 → 自愿提交 Issue。默认不带 Key、文章全文、提示词全文和个人路径。

### 6. 功能需求

#### F01：项目、材料与简报（P0，Beta 必须）

输入：主题、目标读者、目标长度、用户已有材料、可选风格/平台、模型配置。首版支持粘贴文本、UTF-8 Markdown/文本文件及经允许读取的网页文本；扫描 PDF/语音不是必须项。

材料须记录来源类别、导入时间、内容快照/哈希、可见范围。作者素材不能默认跨项目使用。推测与事实分开显示。重要缺口一次追问最多 1–2 个问题；这是交互默认值，不限制用户主动补充。

输出：结构化 `WritingBrief`、`Material` 与用户确认 `Decision`。未确认字段可暂定且标明来源；不能把模型推测标记成用户要求。已有素材采集规则参考 [S06]。

验收：相同简报不因恢复再次索取；无作者亲历来源时禁止输出冒充亲历的要求；路径越界和不支持编码有可操作错误。

#### F02：有边界的自主写作（P0）

保留 quick/deep 的使用语义，但不要求为每一个旧 Stage 建独立 agent。默认执行：材料整理 → 大纲/方向 → 初稿 → 独立评审 → 主笔集中修订 → 语言检查 → 事实核查 → 交付。

方向已授权时可连续推进；事实/权限阻塞、超预算、核心方向冲突才暂停。允许用户选择逐步共创。快速模式可以减少调研和审稿，但正式交付不得绕过事实门禁。

默认角色：主笔、研究/核查能力、只读评审。首版评审可串行。若以后并行，所有评审必须绑定同一版本；只能由主笔或用户提交正文，评审不得互相覆盖文章。

将原写作 skills 逐步编译/加载为中性 writing pack，保留文体、素材、作者声音和修订规则；不继续让 Claude 专用路径成为新引擎运行前提。旧 runtime 的同步规则在其仍受维护期间保持有效。[S03]

验收：真实多轮工具闭环；不是多次单次 generate 的 UI 拼接；达到步数/修订限制后明确停下。

#### F03：统一模型接口（P0）

首版先完成一个真实可用适配，Beta 前覆盖两类必要协议路径以便迁移：OpenAI-compatible 工具调用语义和 Anthropic-compatible 工具调用语义。是否某 provider 完整兼容必须测，不以营销名称判断。

接口统一流式文本、工具调用 ID/参数、结束原因、token usage、取消、错误分类。工具参数 JSON 必须完整且校验通过后才执行。模型不支持 tools 或返回非法结构时，不假装运行成功；提供受限草稿模式或明确要求换模型。

首次连接测试区分网络、鉴权、模型标识、流式与工具能力。模型/provider/version 与参数随每次请求记录。Key 不进入模型消息、普通日志和代码仓库。价格未核验时成本显示未知，不显示 0。

不照抄历史 README 中的推荐模型或额度承诺；实现时核验实际可用模型与服务条款。

#### F04：工具注册、能力与权限（P0）

首批工具：读取已授权材料、列出项目材料、提交稿件/修改提案、读取版本、提交审稿建议、读取网页/检索（配置存在时）、发起核查材料收集。正式导出由用户命令触发并经过硬门禁。

工具先校验参数，再校验权限和目标版本，然后执行并记录结果。工具 schema 在请求快照中绑定版本。无检索凭据时可采用“仅用户材料”模式，明确不能验证外部最新事实，不捏造工具结果。

不提供默认通用 shell。文件访问限定所选工作区和显式导入范围，检查路径穿越与符号链接。网络限制 localhost/私网/元数据端点，默认拒绝非必要协议与重定向绕过。外部材料是数据，不具有更改系统指令和授权的权限。

首版插件为随包交付、经维护者审查的内部模块；进程内插件不是安全沙箱，不允许用户随意安装未知代码后宣称受到隔离。

#### F05：会话、事件与上下文快照（P0）

会话属于项目，一个项目可有多个 run/session。每次准备发送模型的最终可见内容与工具 schema 必须生成不可变快照并记录版本与哈希。记录的是实际组装后的请求内容，不是只记录原始用户消息。

事件按项目递增序列提交；当前状态为事件和版本记录的投影。UI 的实时 token 流可瞬时展示，但已确认结果只能来自持久提交。大文本引用必须指向可取回内容，仅有哈希不能重建原文。

日志可以重建输入和应用状态，不保证重跑远程模型得到相同输出。数据被用户删除后，明确对应历史不再可恢复，不以“不可变日志”拒绝用户删除数据。

#### F06：停止、失败与恢复（P0）

提供暂停/停止/继续。取消立即反馈并传递 abort；已经发出的收费请求不保证可退款。停止后任何迟到结果不得悄悄成为最新稿件。

重启将未结束的 run 标记 `interrupted`，分析持久命令记录。已成功本地操作不重复执行；结果未知的外部操作标记 `unknown_outcome`，需要查询或用户明确决定，不自动假定失败后重做。

第一版保证已提交状态恢复；尚未持久化的流式片段、输入框未保存文字、外部服务内部进度不在保证范围。必须有 UI 明确区分“正在输出”和“已保存”。

#### F07：工件、版本与来源关系（P0）

大纲、正文、标题、证据账本、核查结果、修订提案均为工件。每个版本具有稳定 ID、内容快照、哈希、作者/执行者、父版本、原因、创建事件和时间。

当前稿件通过显式指针指向版本，不能取最新修改时间猜测。新版本不可覆写旧版。回退生成一个新版本，内容可以等于历史版本，但不删除之后的历史。

初期记录工件级与段落级来源图：由哪个版本派生、使用哪些材料、谁接受了哪次修改、哪次核查针对哪个快照。关系以 SQLite 表实现，不需要图数据库或炫目的全景图。只有依赖证据支持时才能建立支持关系，不能由连线本身宣称事实真实。

最小 UI 为版本列表、差异和来源详情。句子级全自动精确来源映射为后续目标。

#### F08：局部修改、锁定与并发保护（P0）

用户可锁定正文段落与已确认标题；模型不能修改锁定内容。修改请求须绑定基准正文版本、目标段落 ID、用户指令和不可改变的约束。

提案先预览差异再接受；接受须做 compare-and-swap 版本检查。基准已过期时返回 `REVISION_CONFLICT`，不自动三方合并。用户可取消、重新基于最新稿生成或自行手动修改。

手动编辑同样创建新版本并校验冲突。对锁定部分的用户更改必须先显式解锁或明确执行解锁操作，不能因操作者是用户就悄悄丢失锁定语义。

#### F09：审稿、事实核查与失效传播（P0）

审稿给出必须修/可选/保留，绑定正文和标题版本，不直接写稿。主笔重大修订默认最多两轮，超过时交给用户决定。

事实门禁保留现有 `fact-check-v2` 的严格语义：全文、最终标题及分发文案覆盖；SUPPORTED 仍须有可定位来源且支持范围 full；UNSUPPORTED、CONTRADICTED、BROKEN_LINK、NEEDS_USER_SOURCE、partial/none 或红色风险阻断。不能把红色改成黄色就放行。[S03][S04]

先冻结正文、标题、分发文案和证据账本，再核查；保存 claims、报告和完整快照哈希。正文等输入发生任何改动，旧报告仍作为历史保存，但当前门禁变为 stale。1.0 采用保守的整组失效，不实现“智能判断这处修改不影响事实，所以复用通过”。

程序判断结构/一致性与状态；语义证据是否真的支持断言仍需模型或人工核对。界面用“此快照通过既定核查流程”，不得承诺事实绝对正确。用户可以补证、改写或删掉断言，但不能用隐藏开关绕过正式交付门禁。

#### F10：保存、正式导出与用户自主权（P0）

**保存工作草稿**一直可用，支持 Markdown/项目备份，并明确未核查或核查已失效。不能以质量门禁阻止用户取回自己的内容。

**正式交付**默认支持 TXT，后续同一门禁下支持 HTML。正式交付按钮和命令须验证最新正文、标题、分发文案、账本和报告的版本关系；失败不覆盖旧导出。为简化验收，HTML 可在 Beta 后完成，但 1.0 前须验证与 TXT 同门禁。

这是对旧导出交互的显式澄清：新增“工作草稿备份”不能借用旧 `_clean.txt`/正式交付名称绕过现有策略，需 ADR 和独立测试。原工作区的 legacy 正式导出规则不被放松。

导出保存对应版本和哈希；文章后来改变时，历史交付仍可查看，但当前页面不得显示“最新版本已通过”。网络自动发布不在 1.0 范围。

#### F11：旧数据迁移（P0，1.0 必须）

支持两类来源：旧 `articles/<project>/` + manifest/Markdown，现有桌面 SQLite + `project.json`/产物目录。M0 先确认实际 schema，不凭历史 PRD猜表结构。

必须提供 dry-run、差异报告、空间检查、独立备份及新目标。默认只读旧源、写入新空间。迁移中断后可安全重试，不产生重复项目。导入身份由来源标识与内容清单绑定。

旧正文、标题、证据、风格、来源明确的决定可导入；未知作者归因标 `unknown/legacy_import`；无事件历史不能伪造。旧 passed 统一标为待重新核查，不自动迁移为新版通过。

旧风格验证状态不升级；旧 `.claude` prompt/agent 文本作为参考资产，未经审查不变成新运行时可执行任意命令。密钥单独征得同意后迁入安全存储，不写进普通迁移报告。

#### F12：成本、诊断与模型能力（P0）

每个 run 显示已用 token、模型调用数、重试数、工具调用数、当前预算与停止原因。provider 不返回 usage 时记未知；可估算但清楚标注。美元/人民币价格必须有版本和核验日期，未知不伪造。

建议起始默认：每个 run 最多 24 个模型步骤、32 次工具调用、每个模型请求最多 2 次可安全重试、主笔重大修订最多 2 轮。数值可在 mock 与真实试验后调整并记录，不是质量保证。重试与子任务必须计入同一预算，不能藏在内部无限循环。

原始日志、开发者诊断与用户播报分开。播报来自真实事件，不伪造进度百分比，不把模型内部推理当可恢复状态。诊断包默认脱敏且由用户预览后导出。

#### F13：风格与作者经验（基础 P0，学习 P1）

首版支持选择/导入现有风格、用户确认的本篇约束与保留其来源。跨文章自动学习放到 1.1 候选：必须有候选规则、用户批准、范围、来源、禁用/删除，不把模型反复建议当成人的偏好。[S06]

#### F14：DSH 前端源码复用与可扩展界面（P0）

**UI-01 源码来源：**新版前端以固定 commit 的 DSH 页面、组件、布局和主题源码为起点，连同必要的 client modules、Slot、状态模型与通信依赖一起审计移植；不以旧 `writing-agent-app` 页面为基础，也不照截图另写一个相似界面。[S13][S14]

**UI-02 首轮保真：**先完成品牌隔离与无关功能裁剪，保留可复用区域的布局、颜色体系、排版、输入、对话、导航和设置交互。以同环境、同内容截图及交互检查比较上游和派生 UI；非必要视觉改动必须列入差异清单，不接受 Agent 自行全面美化。

**UI-03 写作增量：**利用现有面板/Slot 增加稿件、材料/证据、版本/修改、核查/导出视图。沿用组件与主题变量，不重建一套写作页面设计系统。上游文档预览不提供编辑；稿件编辑、锁定和差异接受是本项目须实现的新功能。[S16]

**UI-04 单一真实状态：**UI 通过自有 bridge 调用 Application Service、读取领域投影；没有第二套 UI 核查通过逻辑。跨项目切换、重连、迟到结果、版本冲突遵守运行时契约。不能将 DSH 的 Session 与 WritingProject 强行视为同一对象。

**UI-05 易于调整：**品牌、主题、布局组合、写作功能扩展分别有集中入口。保留适用的上游 Slot/主题机制；改变配色不需改 runtime，新增写作侧栏不需改 agent loop。[S13][S15]

**UI-06 独立性与身份：**前端与后端均在原仓库维护/构建，正式运行不需外部 DSH 服务、CLI、SDK 或旧应用。替换面向用户的品牌、应用 ID、数据路径和官方功能入口；不得继承未经授权的遥测、更新或社区提交端点。用户显式配置的模型 API 不在误禁范围。

**UI-07 历史兼容：**旧 0.1.0 保留历史与数据迁移路径，但新前端/安装包不 import、启动或打包旧 App.tsx、旧全局样式或 Tauri 启动链。旧兼容测试不等于新产品依赖。

**UI-08 可验证交付：**需交付源码来源映射、许可清单、原版与派生截图、改动清单、桥接契约测试、主题/面板扩展测试及独立启动结果。未运行的检查不得标通过。详见 [FRONTEND_REUSE_PLAN](#frontend)。

### 7. 非功能与安全要求

| 编号 | 要求与边界 |
|---|---|
| NFR-01 | 不丢失已成功提交的本地事务；以进程崩溃/中断测试验证。磁盘物理损坏和用户手工删除不在无损承诺内 |
| NFR-02 | 所有修改操作均校验版本与权限；同一项目首版单写者，不支持多人实时协作 |
| NFR-03 | 本地 Web 仅 loopback；校验 Origin/Host，使用每次启动生成的访问凭据，限制跨站请求；不能把 loopback 等同于安全 |
| NFR-04 | Key 保存于系统凭据库；环境变量用于临时开发。没有安全持久化能力时只提供会话内保存，不回退为明文文件 |
| NFR-05 | 搜索/网页抓取受白名单或网络策略限制；拒绝私网/元数据访问，检查重定向与地址解析，外部内容不执行指令 |
| NFR-06 | 模型请求内容快照本地保存；默认不上传遥测。明确云模型会接收到哪些项目内容，支持删除和导出 |
| NFR-07 | HTML 与 Markdown 预览做安全渲染；不执行脚本、事件处理器和危险链接；导出后再次写入正文须重新核查 |
| NFR-08 | 模型延迟之外，交互操作应立即显示本地接受/拒绝状态；建议取消按钮在 1 秒内反馈，远端结束延迟另行显示 |
| NFR-09 | 硬件验收先固定 Windows x64、至少 4 核/16GB/SSD。建议冷启动可操作 ≤5 秒、打开本地 100 个项目列表 ≤2 秒，不含安装/模型网络时间；均待实测 |
| NFR-10 | 每次 release 含依赖锁定、构建环境、检查和与第三方声明；安装包签名有条件就实施，未签名必须如实标示，不指导用户关闭安全机制 |
| NFR-11 | 空磁盘、数据库损坏、schema 比当前应用更新、目录不可写都须显式报错，拒绝静默重置数据库 |
| NFR-12 | 生产依赖不得要求外部 DSH/Claude Code/Python 或旧桌面应用环境；旧测试环境可保留必要工具，分离于新发行产物 |
| NFR-13 | 新 UI 的主题/面板调整有集中入口、类型/行为检查和视觉基线；旧页面引用不得进入新构建闭包 |
| NFR-14 | 前端/bridge/runtime 以同一发行组合验证；协议版本不兼容时明确阻断并提示，不静默混用缓存与新数据 |

“最小权限”是边界限制，不把应用进程内插件或路径校验称为操作系统级沙箱。未知代码扩展需独立进程隔离设计，1.0 不开放。

### 8. 领域模型与状态原则

技术细节以 [RUNTIME_CONTRACTS](#contracts) 为准。最低实体包括：`WritingProject`、`WritingBrief`、`Material`、`Session`、`Run`、`RequestSnapshot`、`Artifact`、`ArtifactVersion`、`Decision`、`RevisionProposal`、`Review`、`FactCheckSnapshot`、`ExportRecord`、`ProvenanceEdge`。

不要把项目、会话和一次模型调用混成一个对象：一篇文章可能跨多个会话和多次 run；一个 run 可能包含很多模型步骤；一个正文版本可被多个只读评审使用。

三个不同维度分别建模：任务执行状态、稿件版本/锁定状态、当前事实门禁。不能用一个 `stage=10` 表示全部信息。

核心不变量：

- I01：已提交正文版本不可变，当前正文指针必须存在且属于本项目。
- I02：正式导出必须匹配当前完整输入快照与有效核查；输入变化即 stale。
- I03：重放本地历史不调用外部模型/工具，不产生新收费或副作用。
- I04：保存正文、更新指针、失效门禁及追加事件在同一事务完成。
- I05：模型不能扩大自身权限、解除用户锁定或自行标记正式交付通过。
- I06：基准版本冲突不能静默覆盖；迟到结果不改变已取消 run 的有效稿件。
- I07：重复操作 ID 不产生重复本地提交；外部未知结果不得假装 exactly-once。
- I08：来源未知就保留未知；来源链不能替代真实性判断。
- I09：未完成迁移、缺少必要记录或遇到未知 schema 均失败关闭，不创造空的新状态冒充原项目。
- I10：密钥不得成为模型上下文、普通日志或传播样本的一部分。

### 9. 建议代码组织与旧资产去向

```text
writing-agent/
  packages/
    runtime/          # 自有 agent loop、session、llm、tools、事件/上下文
    writing-core/     # 稿件、证据、决定、修订、状态与门禁
    storage/          # SQLite、事件/内容存储、迁移与备份
    writing-pack/     # 迁移后的中性写作规则与内置能力
    ui/               # DSH 源码移植的布局/主题/组件/页面；保留来源映射
    client-bridge/    # 移植客户端模型/通信与 Writing 服务的适配边界
    writing-ui/       # 新增稿件、证据、版本/修订、核查/导出面板
  apps/
    cli/              # Writing Agent 自有命令
    web/              # 自有 Web Host 与移植前端入口
    desktop/          # 新分发壳，默认评估 DSH Electron 源码；共享同一 UI
  writing-agent-app/  # legacy 0.1.0 原样保留，仅旧版支持/数据迁移参考
  claude-runtime/     # 旧版唯一源，在迁移结束前继续维护
  plugins/           # 现有 Claude 插件，不直接改成新插件目录
  evaluations/       # 保留原盲评及新增测试夹具
  tests/             # 保留现有测试，逐步补充新测试
  docs/
```

目录是最小建议，不强制把每个概念变成单独 npm 包。暂不建立十几个只有接口没有实现的空包。采用现有包管理方式起步；更换 workspace/包管理器须单独 ADR，不与运行时移植混在同一 PR。

| 现有资产 | 处理策略 |
|---|---|
| `claude-runtime/agents` 与 skills | 逐项抽取宿主无关内容；原路径先保留，避免旧用户断裂 |
| 工作流 JSON 与契约 | 作为旧行为基线；新引擎建立映射及差异说明，不机械复制全部 Stage |
| `fact_check_gate.py` 等门禁脚本 | 先作差分测试基线，再移植为同语义 TS 验证器；Python 不随 1.0 用户环境强制安装 |
| `run_manifest.json` / Markdown | 作为迁移输入与可读导出，不继续让 UI 用文件修改时间猜状态 |
| 旧 Tauri/React 页面及壳 | 不作为新 UI 或分发基线；保留历史、已发布旧入口、迁移夹具和必要 legacy 修复 |
| 旧桌面数据库/文章文件 | 只读导入，移植行为契约而非页面；迁移无需安装或启动旧应用 |
| 原 Demo | 原样保留，标明版本及历史验证状态；新增 1.0 样本，不重写旧历史 |
| 原 tests/evaluations | 保留并记录实际运行结果；迁移测试、新 runtime 测试分别建设 |

### 10. 里程碑、退出标准与执行顺序

里程碑按能力验收推进，不在没有基线的情况下承诺日历日期。每阶段都必须交付运行方法、测试结果和限制说明。

| 里程碑 | 范围 | 退出标准 | 对外状态 |
|---|---|---|---|
| M0 基线与移植设计 | 原项目审计、DSH 前后端闭包/许可、UI 截图计划、ADR、旧回归 | DSH UI 来源、排除旧界面、通信和桌面壳边界明确 | 规划/RFC，不称可用新版 |
| M1 双线移植基线 | 自有 CLI/循环/事件/版本/恢复；并行 DSH UI 本地基线 WA-023 | runtime 闭环可验；移植 UI 独立本地启动，有源码/画面对照；mock 与真实清楚分开 | Alpha，开发者预览 |
| M2 DSH UI 写作化 | 接通自有 runtime；稿件/证据/版本/核查面板；主题与槽位扩展 | 真写作、并发/恢复、视觉基线与 UI 扩展验收通过 | Beta，受限场景预览 |
| M3 迁移与分发 | 只读旧数据导入、新桌面自包含包、诊断、HTML 同门禁 | 同一 DSH 派生前端；无旧应用/DSH 宿主依赖；安全边界与迁移通过 | RC，候选正式版 |
| M4 验证与重发 | 质量盲评、真实上手、文档、原仓库主线切换 | 硬门禁全部满足，维护者审核结果，旧入口与回退文档存在 | 1.0 正式发布 |
| M5 后续候选 | 作者记忆、细粒度复用、专业资料模式、SDK | 由真实需求和数据决定，不计入 1.0 | 独立后续 RFC |

实施分为两条并行线：M0 完成 WA-001–004 后，运行时线推进 WA-005–010，UI 线立即推进 WA-023；两线在 WA-011 接通。随后完成 WA-012–015、WA-024–025 的写作/界面契约，M3 进行 WA-016–018，最后 WA-019–022。精确依赖以 BACKLOG.json 为准，不把数字大小误当执行顺序。安全、UI 来源和视觉基线测试前置。

如果 M1 的 DSH 模块依赖闭包过重，应调整移植粒度并记录 ADR，可保留部分普通框架库；不能以此改回外部 DSH 宿主，也不能直接无分析全量搬仓。

### 11. 验收矩阵

以下是必须由实施 Agent 建立的测试，不是已有通过记录。每项保存复现步骤、工具版本、输入、期望与实际结果；失败不能用注释测试绕过。

| 测试 ID | 场景 | 预期 |
|---|---|---|
| AT-01 | 无 DSH/Claude Code/Python 的干净发行环境启动 | 独立运行、能打开项目和执行写作 |
| AT-02 | 模型提出读材料工具调用，收到结果后生成正文 | 完整多轮 tool-call/result 对应与稿件保存 |
| AT-03 | 重建已记录模型请求 | 系统提示、用户消息、工具结果、schema、参数与快照一致；无网络请求 |
| AT-04 | 提交稿件后强制结束进程再启动 | 最新已提交版本、决定、锁定恢复；未完成 run 显示 interrupted |
| AT-05 | 提交事务前后不同点注入崩溃 | 无半个新版本、旧 passed 配新正文或悬空指针 |
| AT-06 | 相同 operation_id 重复提交 | 返回同一结果，不新增版本或重复导出 |
| AT-07 | 外部请求已发送但结果未知时重启 | 标记 unknown_outcome，不自动反复收费请求 |
| AT-08 | 两个客户端分别基于旧/新版本改稿 | 旧基准被拒绝，已保存用户修改不丢失 |
| AT-09 | 模型修改锁定段落 | 拒绝提交并显示锁定冲突 |
| AT-10 | 取消后收到迟到模型结果 | 可留作无效尝试记录，不更新正式稿件 |
| AT-11 | 核查通过后改变正文、标题、账本、分发文案任一项 | 当前门禁 stale，正式导出阻断 |
| AT-12 | 修改 claims/报告或引用错误 snapshot | 校验失败，不允许历史报告冒充当前结果 |
| AT-13 | unsupported/contradicted/broken_link/needs_user_source/partial/none/red | 均阻断，不得靠 yellow 放行 |
| AT-14 | 无事实声明且覆盖说明完整 | 依既定验证语义处理；不得所有空 claims 一律通过 |
| AT-15 | 未核查稿件请求工作备份 vs 正式交付 | 备份可取回且标注状态；正式交付拒绝 |
| AT-16 | TXT 和 HTML 两种正式出口 | 共享同一门禁；失败不覆盖历史产物 |
| AT-17 | Python 门禁与 TS 门禁对相同规范夹具 | 接受/阻断结果一致；任何差异均有评审说明 |
| AT-18 | 含路径穿越、符号链接的文件工具/导入 | 不越出授权范围，不读取 Key/系统目录 |
| AT-19 | 网页包含提示注入、重定向到私网、危险 HTML | 不扩大权限/泄密/执行脚本，给出明确阻断 |
| AT-20 | 错误 Key、额度不足、无 tools、JSON 截断、429/5xx | 正确分类、受预算约束，无假成功 |
| AT-21 | 旧 manifest 项目/桌面库导入并中断重试 | 不修改旧源、不重复导入、旧通过不升级 |
| AT-22 | 旧风格/未知来源历史迁移 | 保留原验证状态和 unknown，不伪造用户决定 |
| AT-23 | 数据库新版本/损坏/磁盘满/目录只读 | 明确失败，不清库重建；可读取已存在数据时保留读取能力 |
| AT-24 | 生产包依赖与进程扫描 | 无外部 DSH/Claude SDK 引擎依赖；普通依赖有记录 |
| AT-25 | 诊断包与示例发布内容 | 不含 Key、私人正文/路径；脱敏可预览 |
| AT-26 | 达到模型、工具、重试、修订预算 | 统一停止并保留当前产物，不经子任务绕过 |
| AT-27 | 修改完全相同内容、回退到历史稿 | 无意义内容改动不造新内容版；显式回退留新事件/版本 |
| AT-28 | 执行项目删除与备份恢复 | 删除范围明确、不影响别的项目；恢复只基于用户选定备份 |

| AT-30 | 每个移植模块的许可证、来源和上游测试 | 清单可追溯，发行包包含适用声明，测试修改理由明确 |
| AT-31 | 无旧应用、外部 DSH 服务条件下启动移植 UI | 有明确 DSH 源码映射；本地独立启动；仅 mock 时明确标识，不冒充真实写作 |

### 12. 写作质量与产品实验

#### 12.1 控制变量评估

复用既有 12 例合成夹具，至少比较：旧工作流、新 runtime 上的对应写作策略、同模型的简单写作基线。材料、简报、模型/版本、生成参数尽量一致，记录搜索结果快照与生成预算。[S07]

运行时替换实验先保持写作提示词/规则尽量不变，避免同时改模型、素材和流程后无法归因。再单独测试新自主流程、定向修改或素材采访。因工具能力不同导致输入不等价，应明确标注限制。

随机 A/B 身份的人工盲评，关注信息增量、结构、细节、作者声音、阅读吸引力、事实可信度。重大事实错误单独记录并阻止相应样本作为“通过案例”。不以 agent 给自己打分代替人工，不以少量样本宣称统计显著或普遍胜出。

发布门槛：所有夹具完成且结果公开到内部报告；无未处理的重大事实错误漏过门禁；人工未发现跨文体一致的明显质量退步。若大体持平但上手/恢复显著改善，可发布易用性升级，但不宣传质量提升。指标判定有主观部分，需维护者明确签收。

#### 12.2 用户实验与最小指标

建议邀请 5 名目标用户，至少 4 名在不用维护者远程接管的情况下完成首篇真实任务。分别记录安装、模型接入、首稿、修改、交付各步骤阻塞，样例浏览不算真实写作激活。

再邀请有持续需求者在两周观察窗口内尝试第二篇，记录自愿返回人数与原因。这是未来实验设计，不是当前已有留存结果；样本太小不能外推总体。

默认本地记录任务指标，用户自愿导出反馈；不默认收集正文、prompt 或跨项目行为。统计必须有样本分母、观察窗口、失败和缺失项。

### 13. GitHub 与产品传播原则

### 15. 风险、取舍与替代方案

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 只改包名，实际仍依赖 DSH | 启动/恢复调用 dsh CLI/SDK | 独立性测试阻止合入 |
| 移植过多通用功能 | 大量无写作需求对应的插件/配置 | 按需求 ID删减范围，记录依赖闭包 |
| 为摆脱依赖而过度自研 | 重写所有网络/事件框架，无用户闭环 | 允许普通库、选择性源码复用，优先 M1 |
| 模型协议兼容性不完整 | tools/stream/usage 与预设不一致 | 能力探测与实际支持清单，不广泛承诺 |
| 数据丢失与重复操作 | 恢复后重新生成/重复提交 | 事务、版本保护、操作 ID 和 unknown_outcome |
| 事实门禁只剩 UI 标签 | 改稿后仍显示通过 | 领域事务与所有交付入口共享校验 |
| 溯源被误当成真实性 | 显示来源即可通过 | 验证支持范围与人工复核，清楚限制 |
| 上游安全问题继续带入 | 未记录来源与依赖 | 固定快照、安全评审、周期审查上游补丁 |
| 原用户被升级抛弃 | 老路径/风格/数据丢失 | Legacy 入口、只读迁移、文档与备份 |
| 文档大于实际能力 | README 宣布尚未实现功能 | 所有宣传绑定里程碑与验证记录 |
| UI 移植变成重新设计 | 新增全局 CSS、重写全部对话/侧栏 | 先通过 DSH 保真基线，仅允许明确的品牌/写作扩展 |
| 只拷组件忽视协议闭包 | 页面能显示但会话、停止、设置不可用 | 审计 client model/remote/build/host，一并移植必要代码并做契约测试 |
| 上游升级引发合并困难 | 修改散落于原组件、盲目全仓改名 | 固定 commit、集中品牌/主题层、单独上游升级 PR 与视觉测试 |

其他产品方向作为未来实验：资料优先的专业写作模式；作者记忆与风格学习；面向开发者的写作 SDK。它们共享本次领域内核，但未经独立需求验证不扩大 1.0 范围。

### 17. 术语速查

| 术语 | 在本项目中的含义 |
|---|---|
| Runtime 运行时 | 让 agent 真正运行、调工具、记状态、停止和恢复的代码 |
| Harness | 组织模型、工具、会话、策略和入口的外围执行系统；本产品不要求用户理解这个词 |
| Workflow 工作流 | 写作活动的大体顺序，不等同全部状态 |
| State machine 状态机 | 限制哪些状态能在什么条件下改变 |
| Agent loop | 模型提出下一步、执行工具、读取结果后再继续的循环 |
| Event 事件 | 已发生并提交的事实，如某版正文被接受 |
| Projection 投影 | 从事件/记录计算当前可展示或可判断的状态 |
| Artifact 工件 | 正文、大纲、标题、核查报告等正式产物 |
| Provenance 来源关系 | 产物从哪里来、谁改了什么、依据是什么；不是事实真实的证明 |
| Stale 失效 | 旧结果针对的输入变了，不能再作为当前通过依据 |
| Replay 重放 | 读取本地记录重新计算状态，不重新付费调用模型 |
| Recovery 恢复 | 从最后安全的持久化边界继续工作 |
| CAS/乐观并发 | 提交时检查基准版本没变，否则拒绝覆盖 |
| Idempotency 幂等 | 同一操作重复提交，不重复生成本地结果 |
| ADR | 一份短的架构决策记录：决定、原因、备选与验证 |
| 来源清单 | 记录移植代码的上游路径、commit、许可及本地改动 |
| UI shell / 前端外壳 | 页面布局、导航、输入、对话和面板的组合，不等于桌面安装容器 |
| Desktop shell / 桌面容器 | 承载同一前端、启动本地服务并交付安装包的代码 |
| Slot / 插槽 | 在已有界面的指定位置加入新面板或按钮，而不改写整个布局 |
| Design token / 设计变量 | 统一控制颜色、字号、间距等的命名值；不是每页单独调 CSS |
| Client bridge / 客户端适配层 | 把自有写作数据与命令连接到移植的前端，不在 UI 内重建后端规则 |

**实施落点：先把一个真正自主运行、可保存、可恢复、可验证的写作任务跑通，再扩展产品。原仓库积累是升级起点，不是需要被覆盖掉的旧包袱。**

## DSH 前端源码复用与写作化实施方案

文档版本：1.1 · 2026-09-16 · 关联变更：CR-001。目标产品仍为 Writing Agent 1.0。

配套：[PRD](#prd)、[运行时契约](#contracts)、[任务清单](#backlog)、[源码基线](#sources)。本文件是待实施契约，未构建或运行前端，不包含已经通过的视觉测试。

### 1. 已确定的决定，不重新讨论

用户明确选择：**直接利用 DSH 前端源码、页面结构、视觉体系和交互做新版本，避免从零承担 UI 设计，并让后续界面调整集中、可控。**

这不是“参考 DSH 风格重新设计”，不是“在旧桌面界面上换皮”，也不是“给 DSH 安装一个写作插件”。新前端和自有 runtime 都由 `dongbeixiaohuo/writing-agent` 的源码及构建产物负责。来源复用不等于运行时依赖外部 DSH 宿主。

旧 `writing-agent-app` 0.1.0 保留历史与必要兼容说明；它的数据库、文章、模型配置格式可作为迁移输入，但 App.tsx、全局样式、页面组织、Tauri 启动链不作为新版 UI 或应用壳基线。新版本无需安装或启动旧应用即可导入受支持的数据。

**实施顺序：移植原版界面基础 → 完成自有服务适配 → 加入写作面板 → 根据真实反馈调整主题与布局。** 不先重设计，不为了减少几个依赖把已选 UI 全部重写。

### 2. 核对到的上游事实与限制

本次 GitHub 读取的固定 commit 为 `0d1f50007f9bca3f52b06e1c3074fa14d5fb0720`，前端模块地图为 `packages/client/README.md`。[S13]

DSH 前端不是独立静态页面集合。官方文档描述它由浏览器侧 Cordis 应用、Client Modules、API Gateway、Slot 与 Conversation 组成；Host 拥有权威状态，Client model 做镜像，UI adapter 和展示层消费这些状态。[S14] 因此移植必须覆盖所选页面的依赖闭包、必要 Host 接口和类型/构建步骤，不能只复制 `.tsx` 后更换 API 地址。

主题模块提供 light/dark/system、主题快照和 `--dsw-*` 等设计变量；第三方主题可通过别名变量覆盖。它提供的是可扩展基础，不是本产品已经完成的主题编辑器。[S15]

右侧文档预览支持多种只读展示，但官方明确“Preview, not editing”。稿件编辑、锁定段落、接受差异和版本保护需要本项目新增；不能以预览器已经能看 Markdown 为由宣称编辑完成。[S16]

DSH 自身的桌面应用是承载同一 Web UI 的 Electron 壳，带有自身的运行时、协议和分发流程。[S17] 这是可供源码移植的候选，不意味着用户已指定 Electron，更不意味着应复制上游账户、更新服务器和完整插件安装流程。

### 3. 前端移植范围与裁剪表

以下是读取到的上游路径或组名，不代表整个组可以直接单文件复制。每行都要在 `FRONTEND_UPSTREAM_MAP.md` 中列具体源文件、依赖、目标位置、差异、许可和测试。

| 上游范围 | 本版处理 | 验收要求 |

| `ui-brand-official` | 不启用官方品牌模块；用自有品牌模块填充同类入口 | 名称、Logo、页面标题、About/反馈入口为 Writing Agent；法律署名仍保留 |

“直接复用 UI”指保留可用界面基础与交互，不强制保留与写作无关的全部工具，也不允许删到只剩几个按钮再宣称完成。裁剪按功能与依赖分别记录，不猜目录名直接批量删除。

### 4. 目标模块与改动位置

以下为本项目目标模块，不宣称它们是上游已存在的 API。实际目录可在 M0 调整并记录映射；每个逻辑模块不必都是独立 npm 包。

为了方便后续调整，明确四类改动入口：

| 要改什么 | 修改入口 | 不应该修改 |
|---|---|---|
| 颜色、字号、间距、圆角等 | 集中主题变量/别名及覆盖样式 | agent loop、事实门禁、每个页面散落的硬编码 |

上游已有的 CSS token 名、内部标识或来源注释可以保留。不为“去 DSH 字样”大规模改名，避免破坏依赖、样式及后续补丁映射。用户可见品牌、实际启动/网络配置与法律署名要分别处理。

### 5. 先建立保真基线，再扩展写作

#### 5.1 基线 U0

在固定源码版本与合法可用构建环境中，先记录原版 DSH 的关键界面与交互，再建立移植版的同内容参考。上游参考环境仅用于开发比较，隔离测试目录、假数据和凭据；不得把上游参考进程或产物当成新产品运行条件或加入发行包。

至少记录：空工作区、项目/会话导航、普通对话和输入、工具执行中、设置与模型配置、侧栏文档预览。默认以 1440×900 和 1280×800 视口、明/暗主题建立测试夹具；分辨率是测试建议，不是额外移动端承诺。

同一操作系统、浏览器/容器、字体环境、缩放与固定内容下比较。时间戳、动态 token 和授权品牌差异可显式遮罩，其余差异逐项审核；不能整块遮罩关键 UI 让测试通过。视觉比较之外还要测试键盘焦点、输入、滚动、菜单、缩放/面板收放及长中文段落。

可接受差异：Writing Agent 品牌与文案、经过评审的非写作能力裁剪、安全限制、写作功能扩展。不可接受差异：未经授权更改整体设计、混入旧 UI、大面积布局/字体/交互退化。

如果暂时不能运行上游参考，记录缺少的具体构建环境并继续可执行的源码工作；视觉基线标 `BLOCKED_EXTERNAL`，不得用生成图片或自行绘制效果图替代源码运行截图。

#### 5.2 M1 允许的本地 mock

WA-023 可使用桥接接口上的确定性本地 mock，使 UI 先独立运行；页面显著标识“界面移植预览，未接入真实写作”。mock 数据只用于测试，不能写入用户正式项目、报告模型 token 或核查通过。

M2 / WA-011 必须替换为真实 Application Service。测试保留 mock 路径用于确定性回归，但正式构建默认不启用。不能因对话会动就声称自有 runtime 已接通。

### 6. 写作能力如何加入现有 UI

保留 DSH 原有对话、导航和设置体验。稿件可以在现有右侧文档/可停靠区域打开；需要更大编辑区时使用既有面板机制调整，不在首轮改变整个首页信息架构。

| 写作模块 | 放置策略 | 必须新增的行为 |
|---|---|---|
| 稿件 | 现有文档/面板区域，沿用基础控件 | 加载指定 ArtifactVersion；编辑保存、已保存状态、锁定、过期版本冲突 |
| 材料与证据 | 现有资源/右侧 tab 扩展 | 材料来源、快照时间、授权范围、证据支持范围及正文位置 |
| 版本与修订 | 现有 tab 或文档工具栏扩展 | 版本列表、修改理由、差异预览、接受/拒绝/回退 |
| 核查与交付 | 现有状态展示和独立面板 | passed/stale/blocked 与绑定快照；工作备份和正式导出区别 |
| 简报与作者确认 | 对话内卡片/现有问题交互扩展 | 明确暂定与已确认、已给授权不重复问、不可编造作者素材 |

复用 Slots 作为本项目内部组件扩展方式，不等于把本产品改成“运行在 DSH 中的插件”。新增模块与移植模块一起在本仓库构建和发行。

1.0 不做可拖拽页面设计器或在线主题市场。先提供集中配置和内部扩展范例，验证维护者日后改界面不用重写核心。

### 7. Client bridge 与状态映射

默认沿用源码移植后仍有价值的 typed Remote/Client model/Slot 架构，减少前端重写。保留必要生成器和构建脚本，精确固定普通库版本。需要替换 transport 时单独 ADR，证明可减少耦合而非把成本转嫁给每个页面。[S14]

最小映射为：

| 原前端所需能力 | 自有领域语义 | 错误边界 |
|---|---|---|
| 会话/工作区选择 | workspaceId → projectId → sessionId | 一个项目可跨会话；不得只用当前聊天 ID猜项目 |
| 提交输入 | 当前项目的 run.start/有权限的会话命令 | 不直连 provider，不绕过预算或请求快照 |
| 停止/继续 | run.cancel/run.resume | 取消迟到结果不成为正文；重连不触发 resume |
| 对话/执行历史 | 已记录 session/run 事件的展示投影 | 不把 UI 记录当权威历史，不显示虚构工具完成 |
| 稿件和编辑 | artifact.get/body.save/revision.propose/accept 的实现语义 | 带版本与 operationId，冲突不得静默覆盖 |
| 主题/设置 | 自有 settings 服务与凭据引用 | 不读取 `~/.dsh` 或旧应用目录作为运行前提 |
| 导出 | export.working_copy / export.publication | 正式交付统一门禁；不把普通文件下载伪装成核查通过 |

`artifact.get` 在此仅为查询语义示意，具体查询端点与其余命令一同写入实现契约；不得假称已经存在。所有命令输入须由后端运行时验证。

Client model 维护读模型与临时界面状态；事实核查、当前正文指针、来源归因仍由服务端提供。用户看到“已保存”必须已经成功持久提交。项目切换、旧请求迟到、流式内容、完整快照、重连补读分别验证，不能用最后响应覆盖一切。

协议握手记录 client/bridge/runtime 的兼容版本。旧静态资源配新服务时明确报错或安全刷新，不能继续使用错配 schema。发行组合统一测试，不要求以后所有内部模块永远使用同一个版本号。

### 8. 品牌、权限、网络与分发隔离

必须审计页面标题、品牌模块、图标/资源许可、欢迎与帮助入口、模型 onboarding、反馈提交、遥测、更新源、插件源、外部链接、桌面 appId/协议/安装路径/数据目录。保留法律来源声明，但不得以 DeepSeek 官方产品身份展示。

不得沿用上游默认遥测、反馈上传、更新服务或插件分发服务器。未来本项目自有更新服务须另行配置并核验；尚未实现时禁用并使用明确的手动 Release 更新指引。用户主动配置并授权的 DeepSeek 或其他模型 API，以及用户点击官方说明文档，是不同用途，不做机械域名一刀切。

自有进程不因出现 `dsh` 字符串就失败：来源注释、版权、CSS 变量、内部协议格式映射属于允许项；外部 DSH CLI/SDK 执行依赖、读取上游 home、连接已运行 DSH server 则不允许。独立性检查以真实依赖与行为为准。

DSH 的只读 HTML 预览文档描述了脚本沙箱能力。[S16] 本项目首版更保守：不执行用户/模型/网页材料中的脚本，不移植其 `allow-scripts` 行为；仍保留必要安全文档展示。这个安全差异必须纳入上游改动清单，不能被视觉保真要求覆盖。

桌面默认优先移植 DSH Electron 最小壳及必要 host/transport 思路，并替换为 Writing Agent 启动与资源路径。[S17] 保留受限渲染器边界；若采用 Electron，显式验证 `contextIsolation`、禁 renderer Node 集成、受限 preload/IPC、自定义协议路径校验、导航与外链处理。不得把 Electron 自带 Node 当成一定可以运行全部 native 模块；实际携带匹配 runtime 并验证。

桌面发行不要求复刻上游包管理、在线插件安装、自动更新或所有操作系统。仍以 Windows 自包含包为首版目标；Web 与桌面共享同一 UI 和领域契约。其他容器必须有维护者批准的 ADR，不恢复旧 Tauri 路线、不新增第二套新前端。

### 9. 上游来源、补丁与后续 UI 调整

固定 upstream commit，记录每个移植模块的原路径、文件 hash、目标路径、许可、依赖、保留/删除内容和对应测试。必要普通库可使用；从上游复制的配套库若含自有补丁，记录其具体来源，不把它当成可随意换成最新版的同名依赖。

首次引入保留源码边界，后续品牌、主题、bridge、写作扩展尽量独立提交。集中覆盖不等于绝不修改上游组件；确需修改时记录理由与关联测试，避免把维护成本藏起来。

后续同步上游采用专门 PR：对比固定 commit → 选择有关修复 → 复核依赖和许可 → 运行行为/视觉/安全测试 → 维护者决定合入。不承诺自动获得所有社区魔改；具体第三方 UI 代码的来源、许可与兼容性需要另行核查。

版权与许可随发行交付。来源登记和合法 UI 复用不等于品牌授权；不得将来源 Logo 原样当成自己的应用标识。字体/图标等资源按实际许可逐项审计，本交接包不附带任何字体文件。

## Writing Agent 1.0 运行时与领域契约

文档版本：1.1 · 2026-09-16。配套 [PRD](#prd)。本文是建议实现契约，不宣称这些类型或端点已存在。

本文对 PRD 的 P0 要求给出可编码的边界。参数默认值可经 ADR 调整；独立性、数据安全、版本一致性和门禁不得因实现困难而默默取消。

### 1. 结构与依赖方向

```text
CLI / DSH 源码派生 Web UI / 新桌面容器（同源 UI）
          │  同一应用命令与事件协议
          ▼
Application Service
     ├── Writing Core：项目、稿件、证据、锁定、修改、核查、导出
     └── Runtime：agent loop、session、模型、工具与预算
                     │
             Storage / Provider / Capability
```

- `writing-core` 不依赖 React、Electron/Tauri、DSH CLI、Claude SDK 或具体 provider。
- `runtime` 不硬编码正文文件名和旧 Stage 编号；通过领域工具完成写作操作。
- `storage` 提供事务、事件和内容快照。状态机与 gate 不藏在 UI 点击处理器中。
- `Application Service` 是所有修改入口的授权与事务边界，CLI/Web/桌面调用相同命令。
- 来源代码可在本仓库实现上述模块，普通 Cordis 等框架库可按 ADR 使用；不得调用外部 DSH 程序/SDK替代自己的应用执行。

### 2. 关键实体

| 实体 | 必要字段 | 说明 |
|---|---|---|
| WritingProject | id, name, schemaVersion, revision, latestBodyVersionId, currentTitleVersionId, currentEvidenceVersionId, mode, createdAt | revision 是并发保护的项目状态版本，不是文章第几稿 |
| WritingBrief | projectId, versionId, genre, audience, lengthTarget, materials, constraints, interactionMode, authorAuthorization | 假设和用户确认分开 |

| Material | id, projectId, sourceKind, sourceReference, importedAt, contentVersionId, hash, trustLabel | 网页需记录抓取时间与实际读取片段；URL 不能替代快照 |

### 3. 持久化策略：一个事实来源，不双写两套权威状态

#### 3.1 默认实现

首版使用本地 SQLite。默认每个 workspace 一个数据库，路径类似 `<user-selected-workspace>/.writing-agent/workspace.sqlite3`，该路径由设置决定，不放入代码仓库。

建议逻辑表：`projects`、`sessions`、`runs`、`events`、`operations`、`artifacts`、`artifact_versions`、`request_snapshots`、`materials`、`decisions`、`revision_proposals`、`reviews`、`fact_snapshots`、`fact_assessments`、`exports`、`provenance_edges`、`migration_runs`、`schema_migrations`。

首版以文本/Markdown为主，工件正文和请求快照内容可直接入库，保证事务一致性。`events` 保存领域变化，引用不可变内容；`projects/runs` 等当前状态是事务内更新的可重建投影。事件、引用内容和 schema 一起构成恢复事实来源，不能说仅靠 event ID 就能恢复正文。

项目目录中的 `.md`、`run_manifest` 兼容输出和 HTML/TXT 均是从当前记录生成的可读副本/导出，不是第二个写入权威源。用户在文件管理器修改副本时，必须经显式导入创建新版本，不自动更新数据库或假定原核查仍有效。

数据库 journal/同步级别、驱动和备份实现由 ADR 固定。在线备份使用驱动支持的一致性备份，或应用停写后的完整快照，不能只随手复制一个仍在写入的数据库文件。

#### 3.2 大文件与文件系统副作用

1.0 可限制单材料/单项目规模并明确错误，避免无限占用。若内容移到内容寻址文件存储，必须先原子落盘并确认可读，再事务记录引用；失败产生的孤立文件允许后续清理，不能反向出现有引用无内容。

正式导出文件先写同目录临时文件，校验 hash，再原子替换目标。数据库提交和文件系统不能凭空形成一个事务，需 `Operation` 状态与重启对账：若文件已写且 hash 与预期一致，可补记完成；结果不一致则停止并提示。重试不产生多份同名发布，也不覆盖不同来源的文件。

### 4. 事件契约

事件表示已经发生的事实，不是模型计划。最小形状：

```ts
type Actor =
  | { kind: 'user'; id: string }
  | { kind: 'agent'; id: string; runId: string }
  | { kind: 'runtime'; id: string }
  | { kind: 'legacy_import'; id: string };

interface DomainEvent<TPayload> {
  id: string;
  schemaVersion: number;
  projectId: string;
  projectSeq: number;
  type: string;
  occurredAt: string;
  actor: Actor;
  operationId: string;
  causationEventId: string | null;
  correlationId: string;
  payload: TPayload;
}
```

事件类型最小集合：

```text
project.created
brief.confirmed
material.imported
decision.recorded / decision.revoked
run.started / run.paused / run.interrupted / run.resumed
run.cancelled / run.failed / run.completed / run.budget_exhausted
request.prepared / request.dispatch_attempted / request.completed / request.failed
request.outcome_unknown
tool.requested / tool.completed / tool.failed / tool.outcome_unknown
artifact.version_committed
revision.proposed / revision.accepted / revision.rejected
review.recorded
fact.snapshot_created / fact.assessment_recorded / fact.invalidated
export.requested / export.completed / export.failed
migration.started / migration.completed / migration.failed
```

所有事件提交后再通知 UI；UI 订阅断线时按 `projectSeq` 补读，不能把页面重连当成新任务。流式 token 可另走瞬时事件，不提升成已提交稿件。一次发包是否真的被远端接收有不确定窗口，`dispatch_attempted` 不能被解释为服务端已执行或未执行的绝对证明。

#### 4.1 请求可重建约束

保存最终系统内容、已接受的用户消息、工具调用/结果、注入材料内容、模型标识与参数、工具 schema、适配器/模板版本。provider 特有的转换也需版本记录；无法原样重建的字段须明确标识。

发送用 API Key 属于鉴权头/安全配置，不属于模型可见文本，不写入快照。若用户输入误带密钥，应先按策略拦截或脱敏，再发送并记录实际脱敏内容。不能先把一份发给模型，再保存另一份假称完全一致。

不读取或承诺恢复模型内部隐藏思考。日志可解释输入和发生的操作，并不能给出模型真正的内部因果过程。对“同样输入再次生成完全相同输出”不作保证。

### 5. 三组状态，不混成一个 stage

#### 5.1 Run 执行状态

```text
queued → running → completed
             ├→ waiting_user → running
             ├→ paused → running
             ├→ failed
             ├→ cancelled
             ├→ budget_exhausted
             └→ interrupted → waiting_user / running / failed
```

`completed` 表示本次任务结束，不代表文章通过核查或已经导出。终态 run 不能因迟到回包恢复为 running。用户继续修改可创建新 run，保留历史。

`interrupted` 的恢复入口先对账 operations；未知外部副作用必须进入 waiting_user。`budget_exhausted` 后增加预算需用户决定事件，再创建新 run 或明确授权恢复，不由 agent 自己增额。

#### 5.2 RevisionProposal 状态

```text
proposed → accepted
         → rejected
         → conflicted
         → withdrawn
```

接受时需要匹配基准版本和锁定约束；同一提案不能重复生成多个有效正文。用户撤回已接受结果，应通过新版本回退，不删除接受事件。

#### 5.3 当前事实门禁

```text
not_checked → checking → passed / blocked / error
                  └────── 任一输入改变 → stale
passed / blocked / error → 任一输入改变 → stale
stale → checking → passed / blocked / error
```

报告自身是不可变历史结果；这里改变的是项目当前“能否引用该报告”状态。新正文没有核查快照时不得因旧报告 passed 显示绿色。任何不可验证引用一律阻断正式导出。

### 6. 命令、事务与并发

每个修改命令具备 `operationId`、`projectId`、`expectedProjectRevision`、操作者与输入。使用受验证的权限上下文，不相信用户提交的 `actor='runtime'`。

```ts
interface MutationEnvelope<T> {
  operationId: string;
  projectId: string;
  expectedProjectRevision: number;
  payload: T;
}

interface CommitBodyPayload {
  artifactId: string;
  baseVersionId: string | null;
  content: string;
  reason: string;
  acceptedProposalId: string | null;
}

type MutationResult<T> =
  | { ok: true; projectRevision: number; operationId: string; result: T }
  | { ok: false; code: string; message: string; retryable: boolean; details: Record<string, unknown> };
```

`commit_body` 在单一数据库事务中：

1. 检查 operationId：同输入已完成则返回原结果；同 ID 不同 inputHash 返回 `IDEMPOTENCY_KEY_REUSED`。
2. 检查项目 revision、正文 baseVersion、角色权限和锁定段落。
3. 校验内容、计算 hash；若内容未变且不是显式回退，不创建无意义新内容版本，但可记录用户决定/无变更结果。
4. 插入不可变正文版本、来源边及事件，更新 latestBodyVersionId。
5. 使当前核查 stale；必要的标题/评审适用性同步变更，保留历史报告。
6. 更新项目 revision 和 operation 状态，提交事务后发布事件。

首版单进程可用项目级队列序列化写入，但仍需数据库 revision 条件更新，以防多个 UI/进程或恢复后冲突。不要只用前端禁用按钮保护并发。

`projectSeq` 对持久事件排序；`project.revision` 对影响项目有效状态的领域修改做并发检查，二者不等同。瞬时 token/进度广播不推进 revision；纯观察事件无需使正常编辑失效。具体哪些命令推进 revision 必须写进契约测试，不能在各 UI 中各自判断。

如果锁定目标不再能无歧义映射到最新内容，返回冲突，不“尽量找个相似段落”。

### 7. 段落修改与来源图

#### 7.1 首版修改粒度

解析正文为有稳定 `blockId` 的段落/标题块。Patch 包含 `baseVersionId`、目标 blockId、原块 hash、替换内容和修改理由。首版支持替换/插入/删除完整块，不自动三方合并或基于过期字符偏移修改。

自由文本编辑保存时重新解析；能确定保持原块的才复用 ID，不能确定则生成新 ID并标记来源不确定。锁定块不能在此过程中丢失，需要明确解锁或拒绝操作。正文原始内容和解析版本一起保存，以免升级解析器后定位漂移。

#### 7.2 来源图语义

建议关系：`DERIVED_FROM`、`USES_MATERIAL`、`CHANGED_BY_DECISION`、`REVIEWED_IN`、`CHECKED_IN`、`EXPORTED_AS`。

依赖版本派生关系必须无环；并不是所有可能的图关系都强制 DAG。每条证据支持关系应绑定具体断言、证据快照、支持范围、检查来源和时间。存在 `USES_MATERIAL` 不代表正文每句话都被该材料证实。

最小可用查询：这版稿子基于哪版；谁接受了什么改动；为什么当前核查失效；当前导出依据哪一组输入。先实现这些查询，不先实现交互式图谱画布。

### 8. 事实核查与兼容契约

#### 8.1 与旧版的差分验证

现有 Python 脚本和其测试夹具是迁移基线，不是生产中永久 shell-out 的依赖。实施 Agent 先阅读完整 `fact_check_gate.py`、`update_run_manifest.py`、`verify_required_files.py` 及关联测试，再把判断逻辑移入 TS。

把同样输入转为规范夹具，比较 Python 和 TS 的 accept/block 及阻断原因。UUID、时间戳、内部文件路径不必逐字相等，语义门禁必须一致。新增加的安全限制应有 ADR 和新用例，不能称为“无差异迁移”。

#### 8.2 快照与 gate

1. 由 runtime 冻结正文、最终标题、可选分发文案、证据账本及核查策略版本。
2. 模型/人工生成逐条 claims 和来源；覆盖声明需涵盖全文/标题/分发文案。空 claims 必须有合理原因。
3. runtime 校验结构、来源定位、支持范围、风险和 hash 一致性，计算 `passed/blocked`。
4. 核查期间或核查后任一输入改变，旧快照不得作为当前发布依据。
5. claims/报告是不可变输出，手工改动须成为新记录并重验证，不能改个标签就通过。

原协议 claim 枚举保持：`SUPPORTED`、`UNSUPPORTED`、`CONTRADICTED`、`BROKEN_LINK`、`NEEDS_USER_SOURCE`。风险是 `red/yellow/green`，支持范围是 `full/partial/none`。任何非 SUPPORTED、red 或非 full 阻断。

来源是用户本人陈述时，记录为作者提供，不冒充网络验证。是否足以支持特定可核查断言由明确策略决定；首版不得新增一个“用户说了就豁免全部事实”的总开关。

#### 8.3 工作备份与正式交付

`save_working_copy` 不把稿件标成可发布，输出 `.md` 和状态说明，不复用 `_clean.txt`/正式 HTML 入口。`export_publication` 仅在共享 gate 成功后创建导出 operation。

工作备份是数据自主权路径，不是让模型自发绕过核查的替代动作。界面和 CLI 必须明确区分，所有正式出口共用相同核心函数，不允许前端自行判断 passed。

### 9. 工具、模型与取消契约

```ts
interface ToolDefinition<TArgs, TResult> {
  name: string;
  version: string;
  inputSchema: Record<string, unknown>;
  effect: 'read_only' | 'local_idempotent' | 'external_side_effect';
  permissions: string[];
  execute(args: TArgs, context: ToolContext): Promise<TResult>;
}

interface ToolContext {
  projectId: string;
  runId: string;
  operationId: string;
  abortSignal: AbortSignal;
  expectedBodyVersionId: string | null;
  grantedPermissions: readonly string[];
}
```

类型不替代运行时验证：输入必须经 JSON schema/Zod 校验，权限由应用签发，不从模型参数读取。输出长度和可见范围有上限，截断/摘要发生时记录实际注入的版本。

模型 stream 事件最小集合：`text_delta`、`tool_call_delta`、`tool_call_complete`、`usage`、`completed`、`error`。多块工具参数必须完整拼接后验证；tool_call ID 在请求/结果间保持一致。错误或截断不能伪装 `completed`。

模型兼容测试先使用 mock/provider fixture，再在维护者提供授权后做真实工具往返。无工具能力模型只可走明确标记的受限草稿路径，不算 IND/AT 的自主运行闭环完成。

取消标记先持久化再传播 abort，阻止之后提交 active 产物。迟到输出可以保存为 `abandoned` 尝试供诊断，不自动合入正文。再次应用要经过用户明确选择和版本校验。

### 10. 恢复与外部副作用

| 操作状态 | 重启策略 |
|---|---|
| 本地命令已提交成功 | 返回已保存结果，不重做 |
| 本地命令未提交 | 事务回滚后可以在同 operationId 下重新验证执行 |
| 只读工具结果已保存 | 复用快照；需要刷新时创建新 operation |
| 外部请求准备好但确定尚未发送 | 可由恢复策略重新发起，仍检查授权和预算 |
| 已尝试发送且没有确定结果 | unknown_outcome；查询外部状态或让用户决定是否重试 |
| 用户已取消 | 不自动恢复；需新 run/明确恢复授权 |
| 当前 schema 高于程序支持版本 | 只读支持能力内的信息或拒绝打开，不降级写入 |

本地历史重放不触发任何模型/网络工具、文件导出或新用户授权。`replay` 和 `resume` 是不同命令：前者计算状态，后者经过判断后继续执行。

采用快照加事件尾部加速可以，但快照必须含最后事件序列与 schema/hash；删除快照后仍应能从合法事实来源重建。缺少引用内容必须报告缺损，不能悄悄从当前网页重新抓取假称历史重建。

| 错误码 | 面向用户的含义 | 是否可直接自动重试 |

| MODEL_UNSUPPORTED | 当前模型不支持所需能力 | 否 |

| LOCK_CONFLICT | 修改涉及锁定内容 | 否 |
| FACT_CHECK_BLOCKED | 当前事实核查存在阻断 | 否，先处理问题 |
| FACT_CHECK_STALE | 核查不对应当前内容 | 否，重核查 |
| BUDGET_EXHAUSTED | 本轮达到预算 | 否，需用户决定 |

### 13. 源码移植清单与许可证

建议建立 `docs/architecture/UPSTREAM_MAP.md` 与机器清单 `upstream-sources.json`。每条包含：上游 repo、commit、路径、license、source hash、目标路径、移植方式、相关测试、本地改动及维护者。初始清单可只有已计划项，但必须标记 planned/ported/verified，不能把待移植当完成。

`THIRD_PARTY_NOTICES.md` 与适用许可证随发行包一起生成/校验。不是只写 inspired by；也不要求无意义地改名所有函数以掩盖来源。上游源码注释中的版权保留，商标/图片/第三方依赖另外检查。[S10]

CI 检查外部宿主依赖、移植来源记录、license 产物、API schema、schema 迁移和边界测试。最终代码切换与依赖升级单独 PR，减少归因困难。


### 14. 内置扩展模块的最小生命周期

保留类似 harness 的可组合能力，但只实现当前产品需要的内部模块接口：

```ts
interface RuntimeModule {
  id: string;
  version: string;
  requires: readonly string[];
  activate(context: ModuleContext): Promise<() => Promise<void>>;
}

interface ModuleContext {
  getService<T>(name: string): T;
  registerService<T>(name: string, service: T): () => void;
}
```

`getService` 缺少服务时必须明确失败，不能回退成空对象。启动前校验依赖、循环依赖与重名注册；按依赖顺序初始化。初始化失败时逆序释放已启动模块，不留半个可用 runtime；正常退出与取消路径保证 dispose 至多执行一次。

角色/写作规则包可以注册工具、模型适配或领域任务策略，但不能覆盖受保护的门禁、获得未授予权限或绕过 Application Service 提交稿件。内部工具的注册不等于第三方代码隔离。1.0 不做热更新、在线安装或保证 DSH 插件 API 兼容。

这部分可使用经过审查的 Cordis 等普通库来实现，也可使用规模较小的自有实现。M0 记录依赖成本和测试结果后决定，不为了减少一个库而重造整套复杂服务容器。

### 15. DSH 前端移植的客户端契约（CR-001）

完整方案见 [FRONTEND_REUSE_PLAN](#frontend)。这是新产品在原仓库中维护的客户端，不是 DSH 宿主插件。

1. **唯一权威来源：**项目、正文版本、Decision、核查门禁仍归 Application Service/Storage。Client model 只镜像和投影已提交数据；React 组件不持有另一套持久业务状态。
2. **身份映射：**分别保持 workspaceId、projectId、sessionId、runId、artifactVersionId、projectSeq、client generation。初版可每篇默认一个会话，但数据模型不强制一对一。切换项目必须退订旧流并废弃旧页面请求。
3. **命令桥接：**用户输入→run.start/自有 session 命令，停止→run.cancel，编辑保存→body.save，接受修改→revision.accept，正式交付→export.publication。每个写命令携带领域所需的 operationId/expectedRevision；不可直接把对话最后一条回答写成 currentBody。
4. **事件桥接：**持久事件按项目序列补读；流式 token 只做临时显示。bridge 明确映射上游会话事件与自有 run/领域事件，不伪造工具成功。数据推送丢失、重复和乱序按契约测试处理；重连不等于重新开始任务。
5. **版号契约：**客户端、bridge 与 runtime 的 protocolVersion/构建标识随发行绑定，握手不兼容时给出明确错误。UI 缓存不能让旧前端静默读取不兼容的新协议。
6. **内容入口：**上游预览组件是只读能力；编辑另经有版本保护的写作模型。Key 留在凭据边界，真实模型请求由 runtime 发出，不让浏览器绕过预算与请求快照直连。
7. **扩展边界：**写作面板注册到移植的 Slot/布局入口；主题集中为 token/别名覆盖，品牌单独模块。基础组件不直接导入写作门禁实现。必要的新注册 API 名称由本项目定义，不能宣称未实现接口是 DSH 现有 API。
8. **安全覆盖：**上游可预览脚本执行型 HTML 不等于本产品允许。首版仍遵守 NFR-07 的禁脚本安全渲染；相关差异进入上游改动清单与 AT-38。桌面 IPC、自定义 URL、外部导航的允许范围必须明确。
9. **独立性检查范围：**检查实际 imports、打包模块、进程、数据目录和网络依赖，不以代码里出现 dsh 字符串就失败。上游版权、原 CSS token 和合法来源标记可保留；外部宿主启动与旧 UI 引用不可保留。

## 开发 Agent 开工交接

文档版本：1.1 · 2026-09-16。先读 [PRD](#prd) 与 [契约](#contracts)。此文件授予的是实施方向，不是对所有远程/破坏性操作的授权。

### 6. M1 最小竖切面

优先做到：创建项目 → 保存材料 → 自有循环接受模型工具调用 → 工具读材料 → 模型产生稿件 → 提交版本与事件 → 退出进程 → 重启检查 → 显式继续修改。

先用确定性的 mock 模型脚本模拟两次模型请求和一次工具往返。重放测试断言没有外部调用。之后在提供有效模型配置与费用授权时验证真实闭环，记录 provider/model/调用次数/费用未知项。

不要以 `tools: []` 的单次生成、多阶段按钮调用或 `dsh --profile ...` 完成这项验收。不要为演示先写一套临时“假事件流”，真实事件从第一天进入提交路径。

### 6.1 M1 前端最小移植面

先从固定 DSH 快照建立布局、侧栏、对话/输入、主题与设置的源码移植，保持上游可复用区域的默认外观。使用受控本地 mock 建立截图/交互基线，不启动外部 DSH 作为新产品服务，不接旧桌面 UI。移植许可、依赖/构建闭包和品牌隔离一起交付；WA-011 再接实际写作命令。写作扩展、主题与视觉验收按 WA-024–025 完成。

### 7. 修改与测试纪律

- 每个 PR 只做一项可验证能力或一个清楚的依赖模块组。
- 先写失败用例/契约测试，再实现关键规则；特别是版本冲突、核查失效、恢复、幂等、权限和迁移。
- 旧 `.claude` / plugins 镜像不得手工各改一套；通过现有唯一源与同步流程处理。
- 移植 Python 门禁时保留原脚本作为差分基线，不通过删除严格条件适配新模型。
- 页面状态只展示领域结果，不做“UI passed”与后台 gate 两套判断。
- UI 移植先保真，后写作化；禁止 Agent 自行另创设计语言，禁止把旧页面换色称为 DSH UI。
- 品牌/主题/写作扩展分开改动；每个 UI PR 附源码映射、前后截图、交互和协议测试。当前文档没有运行画面，实施时须实际启动并截图，不能编造视觉通过。
- 任何不确定的历史来源保持 unknown；不自动给旧文章补作者决定和核查通过记录。
- 不把正在生成的流式文本标成已保存，不把超时请求一律判失败并自动再次扣费。

### 8. 权限边界

默认可进行已获授权工作区内的阅读、测试、创建特性分支和局部代码修改。以下行为需明确维护者授权：远程发布与仓库设置、创建新的产品仓库、生产数据迁移/删除、付费模型大批量评测、npm 发布、证书和外部服务配置。

模型 Key 缺失时继续 mock 和本地测试；GitHub 写权限缺失时生成 Issue/PR 草稿；签名证书缺失时构建候选包并注明签名限制，不宣称正式发行准备完成。不要反复确认已决定的产品方向。

### 9. 每轮交付格式

```text
任务：WA-xxx / 关联需求与测试
变更：实际修改文件和行为
来源：移植代码的 upstream commit/path，或无移植
验证：实际执行命令、环境、通过/失败/未执行
数据与安全：schema、权限、迁移、Key 是否受影响
限制：没有完成/没有验证的具体项目
下一步：依赖已满足的下一项任务
```

必须区分 DONE、IMPLEMENTED_NOT_VERIFIED、BLOCKED_EXTERNAL 和 NOT_STARTED。没有运行的测试不能写 PASS，没有真实用户/模型验证不能给质量或可用性结论。

### 10. 本阶段不要做

不要沿用旧 0.1.0 页面、旧 App.tsx/全局 CSS 或旧 Tauri 启动链；不要同时维护两套新桌面容器。默认审计 DSH Electron 壳作为同源 UI 的分发方案，必要替代经 ADR 和维护者批准；不要开公开插件市场；不要默认开放 shell；不要给所有模型写未经验证的预设；不要建立空图数据库；不要构造跨文章自学习承诺；不要自动群发和提交到外部内容平台。

若发现完整架构与某个性能优化冲突，优先可恢复、可审计和数据安全。性能和细粒度复用以测量及独立 ADR 推进。

### 1. 仓库策略

唯一产品主仓库继续使用 `dongbeixiaohuo/writing-agent`。不创建第二个面向用户的主仓库，不把旧仓库标归档，不删除 `.git`，不使用 orphan branch/强推覆盖历史。

架构重做不意味着仓库身份重做。同一仓库不需要把 star 从旧分支“搬到”新分支；它仍属于同一仓库。保留 star 不是永久保值承诺，用户仍可以取消收藏。[S01][S11]

#### 分支结构


功能分支小 PR 合到 next/runtime。main 上必要安全/缺陷修复通过正常 PR，并及时合入 next/runtime；避免长期两条分支完全失联。文档 RFC 和预览入口可以提前以小 PR 放到 main，但不能破坏旧安装指引。

不固定一个不存在的旧版 tag。M0 先检查 tags/releases 与实际 commit；有历史 tag 就使用，没有则维护者审核后创建新的明确 legacy tag，不覆盖现有名称。

#### 旧版支持范围

旧分支只保留关键缺陷、安全修复和迁移说明，不承诺同步全部 1.0 新能力。原插件安装路径继续可发现。主线切换前，完整旧文档可存于固定 tag 和 `docs/legacy/` 指引；不把历史源文件挪走后使旧引用全部失效。

旧桌面 0.1.0 保留历史发行与迁移入口，不再扩展为新版 UI。新旧安装包用明确通道与独立应用数据目录区分，不用“自动升级界面”掩盖迁移。

不并行维护两套不断演化的同名写作规则。旧 `claude-runtime` 镜像保持原同步体系；新 writing-pack 的来源和差异显式记录，迁移结束后文档明确哪个运行模式使用哪个版本。

### 3. PR 与 CI 规划

PR 类型至少区分：上游源码引入、行为适配、写作领域实现、数据迁移、依赖升级、文档/发布。源码移植 PR 尽量分成“保留来源的初次导入”和“有测试的本地适配”，让审查者看清原始与修改边界。

每个 PR 描述：相关需求/任务、文件范围、上游来源、用户可见变化、schema 变化、测试及未测试项、回退方式。不可用全仓格式化掩盖逻辑变更。

建议 CI 分组：

| Job | 作用 |
|---|---|
| legacy-check | 原 Python/工作流/同步/插件回归；所需旧宿主只存在于此测试环境 |
| runtime-check | 类型、单测、mock 模型循环、事件重放 |
| writing-contract-check | 版本、锁定、冲突、事实 gate 和 TS/Python 差分 |
| ui-origin-check | DSH 固定源映射、资产许可、无旧 UI/启动链依赖、独立品牌/端点 |
| ui-contract-check | Client bridge、项目切换、重连/取消、Slot 注册与协议版本 |
| ui-visual-check | 固定夹具的上游/派生页面对照、主题、布局、键盘/滚动与差异白名单 |
| security-check | 越权、网络策略、HTML、安全依赖与 secret 扫描 |
| migration-check | 原目录和桌面数据导入、重试、备份与回退 |
| package-check | 安装包内容、无外部宿主依赖、第三方声明及哈希 |
| integration-check | Windows 自包含启动与核心用户旅程 |

初期按任务逐步启用，不建立一堆永远 SKIP 的“绿灯”。真实模型测试单独、显式授权、限预算执行，不在每个外部 PR 自动消耗维护者密钥。

### 4. 版本和发布通道

建议新系统采用同一产品版本序列：`1.0.0-alpha.N`、`1.0.0-beta.N`、`1.0.0-rc.N`、`1.0.0`。若原 tag 冲突，可使用 `runtime-v1.0.0-alpha.1` 等具名 tag；不要移动旧 tag。旧插件版本按其实际维护版本保留，不伪称已经切换 runtime。

GitHub 预览版本标为 prerelease，包含对应目标 commit、支持系统、安装要求、已验证能力、已知限制和回退方式。正式版本明确选取正确 latest，旧版仍可检索。[S12]

npm 通道仅在包名归属与权限核验后建立。目标可用 `next` 对应预览、`latest` 对应稳定，但未发布前 README 不展示貌似可用的安装命令。独立分发与 npm 发布不是同一件事，可先发 GitHub Windows 包。

#### 每次 Release 最低内容

- 精确 tag/commit、操作系统/架构、包版本、模型测试范围。
- 真实安装方式与环境前提，不混淆源代码安装和普通用户安装。
- 更新内容及其验收记录，不把计划功能写成已上线。
- 已知问题、隐私/网络说明、旧数据备份/迁移/回退。
- 安装资产、校验和、适用许可证/第三方声明、签名状态。
- 小而完整的示例，含脱敏材料、稿件、改动、核查状态和复现说明。

### 3. 已知、设计与未知

- **用户明确的方向：**利用 DSH 源码和架构，改造原 Writing Agent 为拥有自有运行时的独立项目；不是依赖 DSH 来运行的插件、profile、SDK 包装产品；保留原项目积累并改善使用门槛和传播。CR-001 进一步明确直接复用 DSH 前端 UI 源码和体系，不利旧 0.1.0 桌面页面，以减少从零设计和后续调整负担。
- **本方案给出的默认设计：**TypeScript 自有 runtime；SQLite 事务记录；M1 并行运行时与 DSH 前端源码移植；M2 接写作服务和面板；桌面默认优先评估移植 DSH Electron 最小壳并自包含分发。具体桌面容器未被用户逐项指定，必要调整须 ADR 与维护者批准，不得恢复旧 UI。先文件/段落级溯源；1.0 前不做公开插件市场。
- **未知：**真实活跃与留存、模型额度/价格、签名证书、完整 OS 兼容范围、DSH 具体移植成本、性能实测、首发模型有效性、用户实际本地数据库格式差异。
- **本次前端补充的事实边界：**只读检查了模块与架构文档；未在运行页面上检查视觉，不以用户提及的其他社区魔改作品作为已验证样本，未移植或构建源代码。
- **本次没有做：**在用户仓库写入文件、创建分支/Issue/Release、运行该项目测试、构建安装包、调用付费模型、做 UI 可用性实验。本包中的测试名称、任务 ID、接口和目录，除明确标注现有者外，均为待实现目标。
