## 1. 为什么需要重新建立基线

本计划建立时，产品主链路仍接近“材料读取 → 单次草稿保存”，原项目的简报、研究、大纲、独立评审、集中修订、语言检查与事实核查尚未完整进入新版桌面主路径。这些后台能力随后接入了真实持久工作流，并在隔离 Windows 桌面候选中用 MiniMax-M3 跑完代表性 Deep 旅程；但真实用户安装试用证明，“后台有阶段”不等于“前台有共创体验”。旧界面仍主要表现为工具状态和最终结果，关键追问、角色交接、阶段判断、基于现稿的自然修改与排版选择不够可见。

因此，2026-09-19 以前的 `READY_FOR_FINAL_USER_UAT` 结论已经撤回。既有真实 provider 结果继续作为运行时证据保留，但不能证明新的交互验收基准。`docs/architecture/IMPLEMENTATION_PROGRESS.md` 中按任务数计算的进度仍只表示 PRD 工程/发布账本；本文件单独记录产品旅程是否达到最终用户验收候选。

## 2. 最终用户验收旅程

1. 用户直接从主对话表达想法、给材料或讨论方向；Agent 依据已经知道的信息和真实缺口决定下一次交流。原“四步引导”解释已由 [CR-003](../../writing-agent-1.0-prd-v1.1-dsh-ui/docs/implementation/CR003_CONVERSATION_FIRST_HARNESS.md)纠正，不能把固定表单或固定问题序列当作 Agent 访谈。
2. 系统展示结构化简报、暂定方向和关键缺口；关键问题一次只问一组，用户明确确认后才开始写作。
3. Quick/Deep 均执行真实、有边界的工作流；Deep 至少包含材料整理、研究/反证、大纲、草稿、三类评审、集中修订、语言检查和事实核查。
4. 用户始终能看到“哪个角色正在做什么”、当前阶段、已完成阶段、阶段成果、失败原因和下一步；不展示模型私有推理，也不把内部工具名当作产品交互。
5. 提纲、初稿和读者审校等共创节点必须提出可回答的问题，允许用户输入具体意见；意见写入同一 run 的恢复指令并影响下一阶段，不能只有一个无语义的“继续”按钮。
6. 成稿后的自然语言要求（例如“压缩到 3000 字”“开头更直接”）必须先读取当前保存稿件，以它为修改基线；不得从零重写后冒充在原稿上修改。
7. 稿件、阶段产物、版本、局部修改、锁定、回滚和核查失效都绑定真实持久状态。
8. 用户可以主动执行事实核查；未通过时看到具体阻断项，通过后才能正式导出。
9. 发布不是单个固定 HTML：至少能选择清爽阅读、杂志长文、紧凑报告三种真实排版预设，并导出内容不同、仍通过同一事实门禁的 HTML。
10. 发送或继续后自动跟随最新状态；用户主动向上阅读时不强制抢回滚动位置，并提供“回到最新”。
11. 用户点击已有项目即可恢复它的当前、可继续或最新会话；项目和会话都有明确可读的选中状态。
12. 提纲等阶段成果在主对话自动展开并渲染 Markdown；事实 `blocked`/`stale`/错误在主对话显示具体主张、建议动作和处理入口。“稿件与版本”只承担历史追溯与精细调整。
13. 在 Windows 桌面候选包中用真实 provider 完成一次代表性全旅程，错误信息能指导用户处理问题。

## 3. 实施批次

### P0-A 完整简报与材料交互 — `真实环境验证`

- 扩展 Bridge 协议和项目创建输入，移除硬编码文体、风格、方向和平台。
- 新建项目保存为待确认简报；首页展示简报、材料、暂定项和缺口。
- 用户确认后才开放写作输入。
- 支持多份粘贴材料及带来源 URL 的网页快照材料；来源 URL 做格式验证。

验收：创建后的持久简报与用户输入一致；未确认不能启动；确认后无需重复询问相同字段。

### P0-B 可执行写作工作流 — `真实环境验证`

- 将 `policy_only` 阶段接入运行时，而不是只放在提示词中。
- 持久化研究/证据、大纲、三类只读评审、正文修订和语言检查产物。
- 评审绑定同一草稿版本；只有主笔路径能够提交正文。
- Quick/Deep 使用不同但明确的有界任务序列。

验收：代表性 Mock 与真实 provider 运行均产生可查询阶段产物和最终正文；缺失必需阶段时不得伪装完成。

### P0-C 进度、运行记录和反馈 — `真实环境验证`

- 在主界面显示工作流阶段条、活动阶段和持久结果。
- 启用“运行记录”，展示请求、工具、阶段、耗用和终止原因。
- 修复发送后自动跟随最新内容及“回到最新”提示。
- 将模型、工作流和工具错误转换成可行动的用户文案。
- 将已有项目行变成可导航入口，并对当前项目/会话提供强视觉与 `aria-current` 语义。
- 阶段成果在主对话直接渲染，不再以默认折叠或原始 Markdown 作为主交互。

验收：用户发出指令后立即看见已接收和当前阶段；不需要手工向下拖动画面判断是否卡住。点击历史项目能直接回到它的对话，选中状态无需猜测；提纲在对话中可直接阅读且无原始 Markdown 符号。

### P0-D 事实核查与正式交付 — `真实环境验证`

- 增加用户可执行的事实核查命令，并生成严格 `fact-check-v2` 结果。
- 展示每条主张、证据、风险、状态与建议动作，隐藏内部 UUID 作为主要文案。
- 正文、标题或证据变化后立即使旧核查失效。
- 只有当前快照核查通过时启用正式 TXT/HTML 导出。
- 需要用户处理的阻断先出现在主对话；用户要查单条证据或历史快照时再进入“稿件与版本 → 核查与来源”。

验收：无事实主张、支持、缺证和矛盾四类样例均按门禁规则处理；不能由模型一句“已通过”绕过程序门禁。

### P0-E 旧版最终用户验收候选 — `历史证据保留 / 新基准已失效`

- 跑全量类型、Runtime、Bridge、UI、Desktop、旧版回归和分发检查。
- 构建隔离 Windows 测试包并执行真实 provider 全旅程。
- 按本文件第 2 节逐项留下截图、事件、版本和导出证据。
- 未执行的独立干净机、真实用户和公开发布仍单独标注，不冒充完成。

旧结果证明运行时、持久化和事实门禁可以工作；真实用户反馈已经证明它不足以支持新的“持续共创”完成结论。

### P0-F 连续共创体验恢复 — `真实环境验证 / 待最终用户签收`

- 新建项目改为四步引导式访谈，默认 Deep + 逐步共创；创建后仍先复核简报，不立即调用模型。
- 阶段展示增加人类可理解的角色；提纲、初稿、读者审校检查点显示成果摘要、下一角色和自由文本反馈。
- 共创反馈通过 Bridge/Host 写入 `resumeDraft.userInstruction`，并受 4,000 字符和检查点状态约束。
- 已有正文后的新消息强制先读取当前正文版本，再把它作为本轮编辑基线。
- HTML 正式导出增加清爽、杂志、紧凑三种真实 CSS 预设；仍复用同一事实门禁。
- 演示场景覆盖“提纲反馈 → 初稿 → 再次反馈”，并实测发送后滚动距离底部为 0。
- 主对话恢复历史项目，直接展示已渲染的阶段成果、完整稿件和事实阻断；工作台不再是获知关键状态的必经入口。

验收：Runtime、Bridge、UI、Desktop 全量回归通过；协议 v17 当前安装包完成打包后握手，历史安装/升级机制另有实机证据；生产界面完成四步建简报，真实 provider 完成“读取现稿 → 提纲反馈 → 初稿反馈 → 审校反馈 → 压缩现稿 → 核查 → 选择排版导出 → 重启读回”。主对话专项回归另外覆盖有/无会话项目导航、选中语义、项目删除、阶段成果 Markdown 渲染和阻断处理入口。这些是历史工程证据；据此恢复 `READY_FOR_FINAL_USER_UAT` 的判断已撤回。当前为 `BLOCKED_CORE_WORKFLOW`，只有 CR-002 业务场景通过后才可申请最终用户签收。

## 4. 进度报告规则

- 工程基础设施完成度与产品旅程完成度分开报告。
- `policy_only`、只读投影、Mock fixture 和未接 UI 的能力都不算用户功能完成。
- 每项只能标记为：`未接入`、`部分闭环`、`本地闭环`、`真实环境验证`、`最终用户签收`。
- “可以最终用户验收”至少要求所有 P0 项达到 `真实环境验证`；实际签收必须由真实用户完成。
