## 1. 背景与讨论结论

### 1.1 用户要解决的问题

现有产品承担两项任务：帮助用户完成可控写作；证明并传播一套有价值的开源写作方法。下一阶段希望减少安装与使用负担，提升技术自主性，同时延续原仓库的 star、历史、样本和社区关系。

用户的核心意图不是“换一个宿主跑原有 skills”，而是“借鉴 DSH 已实现的运行时能力，把 Writing Agent 本身变成一个类似 harness 的独立 agent 系统”。产品仍专注写作，不转成通用 coding agent。

### 1.2 保留的讨论结论

- 保留原仓库和产品名称；在新分支开发，成熟后作为原项目的大版本升级。
- 复用已有写作方法、真实素材规则、事实门禁、风格资产、版本记录和评测，不因其载体是提示词或 Python 脚本就全部重写。
- 借鉴 DSH 的模型调用、工具执行、会话事件、生命周期和扩展接口；稿件、证据、作者决定、修改与核查由 Writing Agent 自己定义。
- 直接复用 DSH 前端源码及必要依赖闭包。先保留其现有视觉和交互，再通过主题、插槽和独立写作面板扩展，避免让维护者承担从零设计 UI 的工作。
- 保留旧桌面用户数据不等于保留旧桌面界面；0.1.0 页面、样式、Tauri 启动路径不进入新产品关键路径。
- 将关键规则提升为程序契约：模型负责创作与建议，程序负责状态、权限、版本一致性和交付门禁。
- 优先完成可以运行、停止、恢复、修改、验证的最小闭环，随后扩展，不先建设插件市场。
- 传播必须展示真实可用性和差异，不把代码重构、agent 数量或 star 数当作写作质量证据。

### 1.3 明确撤回或不采用的讨论路径

早期讨论中“以 DSH SDK/profile 为底座”“把写作做成 DSH 插件”的建议不适用，本 PRD 明确排除。初稿中复用旧 0.1.0 桌面页面和已有 Tauri 壳的路线亦已撤回；不得把 DSH 的 UI 源码复用降级为截图模仿或零散组件参考。另起独立 GitHub 仓库、整体覆盖 main、先完成通用 runtime 平台再做写作，均不是当前方案。

“Writing-visible means recoverable”是本次讨论提出的设计口号，不是 DSH 官方术语。其可测试定义是：**已确认并成功提交、会影响写作结果的状态，可以在重启后从本地记录恢复。**它不承诺恢复未提交的流式文字、模型内部推理，或让再次生成得到完全相同的文章。

### 1.4 当前已确认基线

根包版本为 0.11.0，桌面包版本为 0.1.0；桌面路径已有 React/Tauri、阶段数据结构和 Claude Agent SDK 执行入口。现行 `claude-runtime/` 是旧工作流的唯一源，并已包含正文/标题/证据快照及事实门禁。具体 SHA 与文件见 [S02]–[S05]。

仓库元数据快照为 417 stars、63 forks、4 个 Watch 订阅者，Discussions 尚未启用。该快照不是活跃用户统计。star 本身不产生更新订阅，传播必须另有入口。[S01][S11]

本次没有运行完整测试或安装应用；所有“现有”描述以读取的文档和代码为边界。M0 必须补充代码现状和实际测试结果。

## 2. 产品定位与成功定义

### 2.1 一句话定位

**Writing Agent 是一个本地优先、独立运行、能够围绕素材、稿件版本、证据与作者意图持续工作的开源写作 Agent 系统。**

对作者强调“能用、能改、能继续”；对开发者强调“自有 runtime、明确领域契约、可测试与可扩展”。两种表达指向同一产品，不建立两套实现。

### 2.2 首批目标用户

第一类是愿意提供真实素材、需要写中文观点文/解释文章/经验复盘的个人作者。第二类是现有 Writing Agent 使用者，希望保留资产但降低运行环境依赖。开发者是早期协作者，不是第一版独立 SDK 的承诺对象。

默认首个完整演示覆盖“有材料的中文解释或经验文章”，目标约 1,500–3,000 字，只作为测试场景而非产品字数限制。不把长篇小说、学术论文、自动营销矩阵同时列为首发验收。

### 2.3 产品价值假设

| 假设 | 验证方式 | 失败后的处理 |
|---|---|---|
| 独立分发能减少环境阻塞 | 干净 Windows 环境 + 5 名目标用户上手观察 | 先修安装、连接诊断与引导，不加角色 |
| 版本化修改比整篇重生更可控 | 同一草稿定向修改、锁定段落与回退任务 | 缩小修改粒度或改进冲突处理 |
| 状态与事件记录能降低中断损失 | 自动注入中断、重启、重复请求等故障 | 不发布恢复承诺，先完成恢复测试 |
| 多阶段策略有实际质量价值 | 同模型、同材料的新旧流程及简单基线盲评 | 减少无收益环节，不通过更多循环掩盖 |
| 原社区能帮助验证新版 | 自愿预览报名、真实问题、第二篇创作 | 调整定位与触达，不购买/诱导 star |

### 2.4 非目标

1.0 不做多人协作、云账户/计费体系、自动对外发布、任意远程执行、公开插件商店、与所有 DSH 插件兼容、通用 coding agent、自动经营内容账号。语音/PDF/OCR、多平台精细排版、复杂作者记忆学习、图数据库可视化、跨版本智能合并放到后续。

不承诺完全离线 AI：应用本地运行不意味着云端模型或检索无需联网。不承诺零错误写作或任意模型可用。

## 3. 独立 runtime 的产品与技术边界

### 3.1 必须满足的“独立”标准

**IND-01** 用户不需要安装或登录 DSH，不读取 `~/.dsh` 作为运行前提，不执行 `dsh` 启动命令。

**IND-02** 新产品的启动、会话、循环、工具调度和数据格式由原 Writing Agent 仓库的源码及构建产物负责。运行时不导入外部发布的 DSH SDK/core 包来承担这些职责，也不把 Claude Agent SDK 作为新引擎。

**IND-03** 允许按许可把 DSH 源文件及必要依赖闭包移入本仓库后适配；移入源码属于 Writing Agent 的维护范围，保留清晰上游来源。普通开源库如 Cordis、SQLite 驱动、React 或模型 HTTP 客户端可使用，须说明用途、固定版本并审查许可。

**IND-04** 打包产物经依赖、进程与文件访问测试，确认无 DSH/Claude Code 宿主依赖。仅把包名改掉但仍调用宿主不算通过。

**IND-05** 不主张移植代码为全部原创；许可证与来源说明随源码及发行包一起交付。[S10]

### 3.2 默认实现路线

选择“依赖闭包明确的源码模块移植 + 必要的写作领域重构”。不是不经分析地复制整个仓库，也不是为了纯原创从零复写所有通用能力。

M0 对每个候选模块记录：原路径、commit、必要依赖、上游测试、拟保留接口、目标路径、许可、删除/适配内容、验证方法。DSH 的插件与服务之间存在关系，必须按最小可测试模块组处理，而非随意复制单文件。[S09]

| DSH 参考模块 | 默认动作 | 首版不带入的部分 |
|---|---|---|
| session 与相关事件/上下文投影 | 评估复用类型与投影逻辑，适配自有数据存储 | 上游全部历史格式迁移链 |
| agent / agent-loop | 移植最小运行闭环和可验证生命周期 | 完整通用调度平台 |
| llm 接口与一个适配路径 | 统一流式、工具调用、取消和错误语义 | 不经测试的全部 provider |
| tools / scope / policy | 复用或适配注册、参数校验、权限及执行记录 | 默认开放任意 shell/任意进程 |
| system-prompt/context | 复用请求组装思想，绑定内容快照 | 依赖外部配置层的完整产品组合 |
| Web UI 基础与页面 | **必须源码级移植**：布局、侧栏、会话/输入、主题、基础组件、设置、必要的客户端模型与通信闭包 | 旧 0.1.0 页面混入；默认重设计；未经审查的官方品牌、遥测、账户、更新与插件分发入口 |
| Web Host / gateway / client modules | 保留所移植前端实际依赖的启动、构建、类型生成和通信模块；在本仓库适配自有服务 | 为保留 UI 而运行外部 DSH 服务；只换 URL 不处理协议语义 |
| Desktop 源码 | 桌面交付默认优先评估 DSH Electron 源码的最小壳及匹配资产分发，另立 ADR | 复用旧 Tauri 壳作为默认；照搬上游 updater、账号、插件安装及发布基础设施 |

DSH 上游升级只通过单独 PR 审查。初始移植不应伴随所有依赖升级和全仓格式化，避免无法辨别来源与行为变化。

## 4. 产品形态与分发策略

### 4.1 默认顺序

**M0 固定 DSH 前后端源码基线并拆出依赖闭包；M1 同步推进“自主 runtime + CLI”与“DSH 原版 UI 的本地移植基线”；M2 接通真实写作服务并增量加入稿件功能；M3 分发同源前端与自有 runtime，完成 Windows 自包含安装包。**

DSH UI 移植是首要工程工作，不等待后端全部完成才开始。M1 的 UI 可先使用明确标记的本地 mock 建立移植验收，但 Alpha 对外宣称可写作必须已接入真实运行链；mock 不等于功能完成。

本地 Web 不是云 SaaS。新客户端沿用 DSH 的 React/布局/主题/Slot 思路，必要的 client model、remote 类型和 host 通信代码由本仓库拥有。桌面与 Web 共享这一个前端和相同领域语义，不把旧 0.1.0 页面接回来。

桌面容器是独立技术选择：默认优先审计并源码移植 DSH Electron 最小壳，替换上游运行时启动、应用 ID、数据路径和更新配置；这不表示照搬 DSH 所有分发基础设施。[S17] M0 可依据构建、包体、安全与维护成本提出不同容器 ADR，经维护者批准后采用，但不能因此退回旧 UI，也不同时维护 Electron/Tauri 两套新壳。

### 4.2 安装与启动承诺

| 阶段 | 用户承诺 | 不能宣称 |
|---|---|---|
| Alpha | 开发者可按已验证命令启动；明确需要 Node 与构建步骤 | 普通用户零配置 |
| Beta 本地 Web | 在已列出的 Node 版本下用已发布/验证的命令启动 | 没发布的 npm 包已可 npx 运行 |
| 1.0 Windows | 安装包带匹配 runtime，无需用户自行装 Node、Python、Rust、DSH 或 Claude Code | 无 Key、无额度也能调用收费云模型 |

目标命令名称为 `writing-agent web / run / inspect / resume / doctor`，均是待实现接口。npm 包名、命令是否冲突及发布权由 M0 检查；当前根包 `private: true`，不能直接把示例 npx 命令放进正式 README。[S02]

默认本地服务只监听 loopback，禁用公网绑定。非必要不需要账户注册，不上传文章遥测。首次启动引导模型连接、工作目录和数据传输说明。

## 5. 核心用户旅程

### J1：首次写作

安装/启动 → 选择可用 provider 并安全填写 Key → 测试模型能力 → 输入主题与材料 → 显示简报、暂定方向和缺口 → 必要时确认 → 系统自主推进 → 草稿出现 → 局部修改 → 核查 → 正式导出。

目标不是尽量少问问题，而是只问改变方向、作者真实性或授权的问题。已有授权不重复问，非关键缺口可以明确暂定。没有资料时，不伪造作者亲历或虚构搜索成功。

### J2：中断继续

运行时出现连接问题或进程退出 → 重启 → 显示最近已提交稿件、已确认决定、任务状态与未结算操作 → 用户点击继续 → 从安全边界继续。不得把整篇重新生成伪装成恢复。

### J3：定向改稿

用户选中段落，要求改语气但不改事实 → 系统生成相对于指定版本的 patch → 差异预览 → 接受后创建新版本 → 程序使依赖旧正文的核查失效。若用户先手动改过正文，旧 patch 被拒绝并说明冲突，不静默覆盖。

### J4：旧项目进入新版

用户选择旧目录或数据库 → 只读扫描 → 显示将导入的文章、素材、风格和不能恢复的历史 → 建立备份/独立目标 → 导入为新项目 → 保留旧文件 → 需要交付时重新核查。导入旧稿不捏造旧会话与修改链。

### J5：发现问题并反馈

用户查看错误原因、重试边界与诊断信息 → 选择导出脱敏诊断包 → 预览会包含哪些字段 → 自愿提交 Issue。默认不带 Key、文章全文、提示词全文和个人路径。

## 6. 功能需求

### F01：项目、材料与简报（P0，Beta 必须）

输入：主题、目标读者、目标长度、用户已有材料、可选风格/平台、模型配置。首版支持粘贴文本、UTF-8 Markdown/文本文件及经允许读取的网页文本；扫描 PDF/语音不是必须项。

材料须记录来源类别、导入时间、内容快照/哈希、可见范围。作者素材不能默认跨项目使用。推测与事实分开显示。重要缺口一次追问最多 1–2 个问题；这是交互默认值，不限制用户主动补充。

输出：结构化 `WritingBrief`、`Material` 与用户确认 `Decision`。未确认字段可暂定且标明来源；不能把模型推测标记成用户要求。已有素材采集规则参考 [S06]。

验收：相同简报不因恢复再次索取；无作者亲历来源时禁止输出冒充亲历的要求；路径越界和不支持编码有可操作错误。

### F02：有边界的自主写作（P0）

保留 quick/deep 的使用语义，但不要求为每一个旧 Stage 建独立 agent。默认执行：材料整理 → 大纲/方向 → 初稿 → 独立评审 → 主笔集中修订 → 语言检查 → 事实核查 → 交付。

方向已授权且当前输入足以支持下一步时可连续推进；材料/事实/权限缺口、超预算、核心方向冲突必须立即暂停并在主对话提问，不能跑完流程后追溯告知。允许用户选择逐步共创；自主模式也不能跳过必要追问。快速模式可以减少调研和审稿，但正式交付不得绕过事实门禁。

默认角色：导演、主笔、研究/核查能力、只读评审。导演依据输入与阶段结果决定委派、提问、返工或等待；专家任务必须有独立上下文和权限，不得以同一会话中的角色标签替代。首版评审可串行；串行或并行的初次评审都必须绑定同一正文版本，且不得看到其他评审意见。只能由主笔或用户提交正文，评审不得互相覆盖文章。

将原写作 skills 逐步编译/加载为中性 writing pack，保留文体、素材、作者声音和修订规则；不继续让 Claude 专用路径成为新引擎运行前提。旧 runtime 的同步规则在其仍受维护期间保持有效。[S03]

验收：真实多轮工具闭环；不是多次单次 generate 的 UI 拼接；达到步数/修订限制后明确停下。另须通过 CR-002 C02-01 至 C02-10：必要信息不足时无后续产物；问题/答复持久化；同 run 补充恢复；导演委派与评审隔离可由请求快照验证；阶段执行完成不冒充文章可交付。

### F03：统一模型接口（P0）

首版先完成一个真实可用适配，Beta 前覆盖两类必要协议路径以便迁移：OpenAI-compatible 工具调用语义和 Anthropic-compatible 工具调用语义。是否某 provider 完整兼容必须测，不以营销名称判断。

接口统一流式文本、工具调用 ID/参数、结束原因、token usage、取消、错误分类。工具参数 JSON 必须完整且校验通过后才执行。模型不支持 tools 或返回非法结构时，不假装运行成功；提供受限草稿模式或明确要求换模型。

首次连接测试区分网络、鉴权、模型标识、流式与工具能力。模型/provider/version 与参数随每次请求记录。Key 不进入模型消息、普通日志和代码仓库。价格未核验时成本显示未知，不显示 0。

不照抄历史 README 中的推荐模型或额度承诺；实现时核验实际可用模型与服务条款。

### F04：工具注册、能力与权限（P0）

首批工具：读取已授权材料、列出项目材料、提交稿件/修改提案、读取版本、提交审稿建议、读取网页/检索（配置存在时）、发起核查材料收集。正式导出由用户命令触发并经过硬门禁。

工具先校验参数，再校验权限和目标版本，然后执行并记录结果。工具 schema 在请求快照中绑定版本。无检索凭据时可采用“仅用户材料”模式，明确不能验证外部最新事实，不捏造工具结果。

不提供默认通用 shell。文件访问限定所选工作区和显式导入范围，检查路径穿越与符号链接。网络限制 localhost/私网/元数据端点，默认拒绝非必要协议与重定向绕过。外部材料是数据，不具有更改系统指令和授权的权限。

首版插件为随包交付、经维护者审查的内部模块；进程内插件不是安全沙箱，不允许用户随意安装未知代码后宣称受到隔离。

### F05：会话、事件与上下文快照（P0）

会话属于项目，一个项目可有多个 run/session。每次准备发送模型的最终可见内容与工具 schema 必须生成不可变快照并记录版本与哈希。记录的是实际组装后的请求内容，不是只记录原始用户消息。

事件按项目递增序列提交；当前状态为事件和版本记录的投影。UI 的实时 token 流可瞬时展示，但已确认结果只能来自持久提交。大文本引用必须指向可取回内容，仅有哈希不能重建原文。

日志可以重建输入和应用状态，不保证重跑远程模型得到相同输出。数据被用户删除后，明确对应历史不再可恢复，不以“不可变日志”拒绝用户删除数据。

### F06：停止、失败与恢复（P0）

提供暂停/停止/继续。取消立即反馈并传递 abort；已经发出的收费请求不保证可退款。停止后任何迟到结果不得悄悄成为最新稿件。

重启将未结束的 run 标记 `interrupted`，分析持久命令记录。已成功本地操作不重复执行；结果未知的外部操作标记 `unknown_outcome`，需要查询或用户明确决定，不自动假定失败后重做。

第一版保证已提交状态恢复；尚未持久化的流式片段、输入框未保存文字、外部服务内部进度不在保证范围。必须有 UI 明确区分“正在输出”和“已保存”。

### F07：工件、版本与来源关系（P0）

大纲、正文、标题、证据账本、核查结果、修订提案均为工件。每个版本具有稳定 ID、内容快照、哈希、作者/执行者、父版本、原因、创建事件和时间。

当前稿件通过显式指针指向版本，不能取最新修改时间猜测。新版本不可覆写旧版。回退生成一个新版本，内容可以等于历史版本，但不删除之后的历史。

初期记录工件级与段落级来源图：由哪个版本派生、使用哪些材料、谁接受了哪次修改、哪次核查针对哪个快照。关系以 SQLite 表实现，不需要图数据库或炫目的全景图。只有依赖证据支持时才能建立支持关系，不能由连线本身宣称事实真实。

最小 UI 为版本列表、差异和来源详情。句子级全自动精确来源映射为后续目标。

### F08：局部修改、锁定与并发保护（P0）

用户可锁定正文段落与已确认标题；模型不能修改锁定内容。修改请求须绑定基准正文版本、目标段落 ID、用户指令和不可改变的约束。

提案先预览差异再接受；接受须做 compare-and-swap 版本检查。基准已过期时返回 `REVISION_CONFLICT`，不自动三方合并。用户可取消、重新基于最新稿生成或自行手动修改。

手动编辑同样创建新版本并校验冲突。对锁定部分的用户更改必须先显式解锁或明确执行解锁操作，不能因操作者是用户就悄悄丢失锁定语义。

### F09：审稿、事实核查与失效传播（P0）

审稿给出必须修/可选/保留，绑定正文和标题版本，不直接写稿。主笔重大修订默认最多两轮，超过时交给用户决定。

事实门禁保留现有 `fact-check-v2` 的严格语义：全文、最终标题及分发文案覆盖；SUPPORTED 仍须有可定位来源且支持范围 full；UNSUPPORTED、CONTRADICTED、BROKEN_LINK、NEEDS_USER_SOURCE、partial/none 或红色风险阻断。不能把红色改成黄色就放行。[S03][S04]

先冻结正文、标题、分发文案和证据账本，再核查；保存 claims、报告和完整快照哈希。正文等输入发生任何改动，旧报告仍作为历史保存，但当前门禁变为 stale。1.0 采用保守的整组失效，不实现“智能判断这处修改不影响事实，所以复用通过”。

程序判断结构/一致性与状态；语义证据是否真的支持断言仍需模型或人工核对。界面用“此快照通过既定核查流程”，不得承诺事实绝对正确。用户可以补证、改写或删掉断言，但不能用隐藏开关绕过正式交付门禁。

### F10：保存、正式导出与用户自主权（P0）

**保存工作草稿**一直可用，支持 Markdown/项目备份，并明确未核查或核查已失效。不能以质量门禁阻止用户取回自己的内容。

**正式交付**默认支持 TXT，后续同一门禁下支持 HTML。正式交付按钮和命令须验证最新正文、标题、分发文案、账本和报告的版本关系；失败不覆盖旧导出。为简化验收，HTML 可在 Beta 后完成，但 1.0 前须验证与 TXT 同门禁。

这是对旧导出交互的显式澄清：新增“工作草稿备份”不能借用旧 `_clean.txt`/正式交付名称绕过现有策略，需 ADR 和独立测试。原工作区的 legacy 正式导出规则不被放松。

导出保存对应版本和哈希；文章后来改变时，历史交付仍可查看，但当前页面不得显示“最新版本已通过”。网络自动发布不在 1.0 范围。

### F11：旧数据迁移（P0，1.0 必须）

支持两类来源：旧 `articles/<project>/` + manifest/Markdown，现有桌面 SQLite + `project.json`/产物目录。M0 先确认实际 schema，不凭历史 PRD猜表结构。

必须提供 dry-run、差异报告、空间检查、独立备份及新目标。默认只读旧源、写入新空间。迁移中断后可安全重试，不产生重复项目。导入身份由来源标识与内容清单绑定。

旧正文、标题、证据、风格、来源明确的决定可导入；未知作者归因标 `unknown/legacy_import`；无事件历史不能伪造。旧 passed 统一标为待重新核查，不自动迁移为新版通过。

旧风格验证状态不升级；旧 `.claude` prompt/agent 文本作为参考资产，未经审查不变成新运行时可执行任意命令。密钥单独征得同意后迁入安全存储，不写进普通迁移报告。

### F12：成本、诊断与模型能力（P0）

每个 run 显示已用 token、模型调用数、重试数、工具调用数、当前预算与停止原因。provider 不返回 usage 时记未知；可估算但清楚标注。美元/人民币价格必须有版本和核验日期，未知不伪造。

建议起始默认：每个 run 最多 24 个模型步骤、32 次工具调用、每个模型请求最多 2 次可安全重试、主笔重大修订最多 2 轮。数值可在 mock 与真实试验后调整并记录，不是质量保证。重试与子任务必须计入同一预算，不能藏在内部无限循环。

原始日志、开发者诊断与用户播报分开。播报来自真实事件，不伪造进度百分比，不把模型内部推理当可恢复状态。诊断包默认脱敏且由用户预览后导出。

### F13：风格与作者经验（基础 P0，学习 P1）

首版支持选择/导入现有风格、用户确认的本篇约束与保留其来源。跨文章自动学习放到 1.1 候选：必须有候选规则、用户批准、范围、来源、禁用/删除，不把模型反复建议当成人的偏好。[S06]

### F14：DSH 前端源码复用与可扩展界面（P0）

**UI-01 源码来源：**新版前端以固定 commit 的 DSH 页面、组件、布局和主题源码为起点，连同必要的 client modules、Slot、状态模型与通信依赖一起审计移植；不以旧 `writing-agent-app` 页面为基础，也不照截图另写一个相似界面。[S13][S14]

**UI-02 首轮保真：**先完成品牌隔离与无关功能裁剪，保留可复用区域的布局、颜色体系、排版、输入、对话、导航和设置交互。以同环境、同内容截图及交互检查比较上游和派生 UI；非必要视觉改动必须列入差异清单，不接受 Agent 自行全面美化。

**UI-03 写作增量：**利用现有面板/Slot 增加稿件、材料/证据、版本/修改、核查/导出视图。沿用组件与主题变量，不重建一套写作页面设计系统。上游文档预览不提供编辑；稿件编辑、锁定和差异接受是本项目须实现的新功能。[S16]

**UI-04 单一真实状态：**UI 通过自有 bridge 调用 Application Service、读取领域投影；没有第二套 UI 核查通过逻辑。跨项目切换、重连、迟到结果、版本冲突遵守运行时契约。不能将 DSH 的 Session 与 WritingProject 强行视为同一对象。

**UI-05 易于调整：**品牌、主题、布局组合、写作功能扩展分别有集中入口。保留适用的上游 Slot/主题机制；改变配色不需改 runtime，新增写作侧栏不需改 agent loop。[S13][S15]

**UI-06 独立性与身份：**前端与后端均在原仓库维护/构建，正式运行不需外部 DSH 服务、CLI、SDK 或旧应用。替换面向用户的品牌、应用 ID、数据路径和官方功能入口；不得继承未经授权的遥测、更新或社区提交端点。用户显式配置的模型 API 不在误禁范围。

**UI-07 历史兼容：**旧 0.1.0 保留历史与数据迁移路径，但新前端/安装包不 import、启动或打包旧 App.tsx、旧全局样式或 Tauri 启动链。旧兼容测试不等于新产品依赖。

**UI-08 可验证交付：**需交付源码来源映射、许可清单、原版与派生截图、改动清单、桥接契约测试、主题/面板扩展测试及独立启动结果。未运行的检查不得标通过。详见 [FRONTEND_REUSE_PLAN](../implementation/FRONTEND_REUSE_PLAN.md)。

## 7. 非功能与安全要求

| 编号 | 要求与边界 |
|---|---|
| NFR-01 | 不丢失已成功提交的本地事务；以进程崩溃/中断测试验证。磁盘物理损坏和用户手工删除不在无损承诺内 |
| NFR-02 | 所有修改操作均校验版本与权限；同一项目首版单写者，不支持多人实时协作 |
| NFR-03 | 本地 Web 仅 loopback；校验 Origin/Host，使用每次启动生成的访问凭据，限制跨站请求；不能把 loopback 等同于安全 |
| NFR-04 | Key 保存于系统凭据库；环境变量用于临时开发。没有安全持久化能力时只提供会话内保存，不回退为明文文件 |
| NFR-05 | 搜索/网页抓取受白名单或网络策略限制；拒绝私网/元数据访问，检查重定向与地址解析，外部内容不执行指令 |
| NFR-06 | 模型请求内容快照本地保存；默认不上传遥测。明确云模型会接收到哪些项目内容，支持删除和导出 |
| NFR-07 | HTML 与 Markdown 预览做安全渲染；不执行脚本、事件处理器和危险链接；导出后再次写入正文须重新核查 |
| NFR-08 | 模型延迟之外，交互操作应立即显示本地接受/拒绝状态；建议取消按钮在 1 秒内反馈，远端结束延迟另行显示 |
| NFR-09 | 硬件验收先固定 Windows x64、至少 4 核/16GB/SSD。建议冷启动可操作 ≤5 秒、打开本地 100 个项目列表 ≤2 秒，不含安装/模型网络时间；均待实测 |
| NFR-10 | 每次 release 含依赖锁定、构建环境、检查和与第三方声明；安装包签名有条件就实施，未签名必须如实标示，不指导用户关闭安全机制 |
| NFR-11 | 空磁盘、数据库损坏、schema 比当前应用更新、目录不可写都须显式报错，拒绝静默重置数据库 |
| NFR-12 | 生产依赖不得要求外部 DSH/Claude Code/Python 或旧桌面应用环境；旧测试环境可保留必要工具，分离于新发行产物 |
| NFR-13 | 新 UI 的主题/面板调整有集中入口、类型/行为检查和视觉基线；旧页面引用不得进入新构建闭包 |
| NFR-14 | 前端/bridge/runtime 以同一发行组合验证；协议版本不兼容时明确阻断并提示，不静默混用缓存与新数据 |

“最小权限”是边界限制，不把应用进程内插件或路径校验称为操作系统级沙箱。未知代码扩展需独立进程隔离设计，1.0 不开放。

## 8. 领域模型与状态原则

技术细节以 [RUNTIME_CONTRACTS](../architecture/RUNTIME_CONTRACTS.md) 为准。最低实体包括：`WritingProject`、`WritingBrief`、`Material`、`Session`、`Run`、`RequestSnapshot`、`Artifact`、`ArtifactVersion`、`Decision`、`RevisionProposal`、`Review`、`FactCheckSnapshot`、`ExportRecord`、`ProvenanceEdge`。

不要把项目、会话和一次模型调用混成一个对象：一篇文章可能跨多个会话和多次 run；一个 run 可能包含很多模型步骤；一个正文版本可被多个只读评审使用。

三个不同维度分别建模：任务执行状态、稿件版本/锁定状态、当前事实门禁。不能用一个 `stage=10` 表示全部信息。

核心不变量：

- I01：已提交正文版本不可变，当前正文指针必须存在且属于本项目。
- I02：正式导出必须匹配当前完整输入快照与有效核查；输入变化即 stale。
- I03：重放本地历史不调用外部模型/工具，不产生新收费或副作用。
- I04：保存正文、更新指针、失效门禁及追加事件在同一事务完成。
- I05：模型不能扩大自身权限、解除用户锁定或自行标记正式交付通过。
- I06：基准版本冲突不能静默覆盖；迟到结果不改变已取消 run 的有效稿件。
- I07：重复操作 ID 不产生重复本地提交；外部未知结果不得假装 exactly-once。
- I08：来源未知就保留未知；来源链不能替代真实性判断。
- I09：未完成迁移、缺少必要记录或遇到未知 schema 均失败关闭，不创造空的新状态冒充原项目。
- I10：密钥不得成为模型上下文、普通日志或传播样本的一部分。

```text
    writing-ui/       # 新增稿件、证据、版本/修订、核查/导出面板
  apps/
    cli/              # Writing Agent 自有命令
    web/              # 自有 Web Host 与移植前端入口
    desktop/          # 新分发壳，默认评估 DSH Electron 源码；共享同一 UI
  writing-agent-app/  # legacy 0.1.0 原样保留，仅旧版支持/数据迁移参考
  claude-runtime/     # 旧版唯一源，在迁移结束前继续维护
  plugins/           # 现有 Claude 插件，不直接改成新插件目录
  evaluations/       # 保留原盲评及新增测试夹具
  tests/             # 保留现有测试，逐步补充新测试
  docs/
```

目录是最小建议，不强制把每个概念变成单独 npm 包。暂不建立十几个只有接口没有实现的空包。采用现有包管理方式起步；更换 workspace/包管理器须单独 ADR，不与运行时移植混在同一 PR。

| 现有资产 | 处理策略 |
|---|---|
| `claude-runtime/agents` 与 skills | 逐项抽取宿主无关内容；原路径先保留，避免旧用户断裂 |
| 工作流 JSON 与契约 | 作为旧行为基线；新引擎建立映射及差异说明，不机械复制全部 Stage |
| `fact_check_gate.py` 等门禁脚本 | 先作差分测试基线，再移植为同语义 TS 验证器；Python 不随 1.0 用户环境强制安装 |
| `run_manifest.json` / Markdown | 作为迁移输入与可读导出，不继续让 UI 用文件修改时间猜状态 |
| 旧 Tauri/React 页面及壳 | 不作为新 UI 或分发基线；保留历史、已发布旧入口、迁移夹具和必要 legacy 修复 |
| 旧桌面数据库/文章文件 | 只读导入，移植行为契约而非页面；迁移无需安装或启动旧应用 |
| 原 Demo | 原样保留，标明版本及历史验证状态；新增 1.0 样本，不重写旧历史 |
| 原 tests/evaluations | 保留并记录实际运行结果；迁移测试、新 runtime 测试分别建设 |

## 10. 里程碑、退出标准与执行顺序

里程碑按能力验收推进，不在没有基线的情况下承诺日历日期。每阶段都必须交付运行方法、测试结果和限制说明。

| 里程碑 | 范围 | 退出标准 | 对外状态 |
|---|---|---|---|
| M0 基线与移植设计 | 原项目审计、DSH 前后端闭包/许可、UI 截图计划、ADR、旧回归 | DSH UI 来源、排除旧界面、通信和桌面壳边界明确 | 规划/RFC，不称可用新版 |
| M1 双线移植基线 | 自有 CLI/循环/事件/版本/恢复；并行 DSH UI 本地基线 WA-023 | runtime 闭环可验；移植 UI 独立本地启动，有源码/画面对照；mock 与真实清楚分开 | Alpha，开发者预览 |
| M2 DSH UI 写作化 | 接通自有 runtime；稿件/证据/版本/核查面板；主题与槽位扩展 | 真写作、并发/恢复、视觉基线与 UI 扩展验收通过 | Beta，受限场景预览 |
| M3 迁移与分发 | 只读旧数据导入、新桌面自包含包、诊断、HTML 同门禁 | 同一 DSH 派生前端；无旧应用/DSH 宿主依赖；安全边界与迁移通过 | RC，候选正式版 |
| M4 验证与重发 | 质量盲评、真实上手、文档、原仓库主线切换 | 硬门禁全部满足，维护者审核结果，旧入口与回退文档存在 | 1.0 正式发布 |
| M5 后续候选 | 作者记忆、细粒度复用、专业资料模式、SDK | 由真实需求和数据决定，不计入 1.0 | 独立后续 RFC |

实施分为两条并行线：M0 完成 WA-001–004 后，运行时线推进 WA-005–010，UI 线立即推进 WA-023；两线在 WA-011 接通。随后完成 WA-012–015、WA-024–025 的写作/界面契约，M3 进行 WA-016–018，最后 WA-019–022。精确依赖以 BACKLOG.json 为准，不把数字大小误当执行顺序。安全、UI 来源和视觉基线测试前置。

如果 M1 的 DSH 模块依赖闭包过重，应调整移植粒度并记录 ADR，可保留部分普通框架库；不能以此改回外部 DSH 宿主，也不能直接无分析全量搬仓。

## 11. 验收矩阵

以下是必须由实施 Agent 建立的测试，不是已有通过记录。每项保存复现步骤、工具版本、输入、期望与实际结果；失败不能用注释测试绕过。

## 12. 写作质量与产品实验

### 12.1 控制变量评估

复用既有 12 例合成夹具，至少比较：旧工作流、新 runtime 上的对应写作策略、同模型的简单写作基线。材料、简报、模型/版本、生成参数尽量一致，记录搜索结果快照与生成预算。[S07]

运行时替换实验先保持写作提示词/规则尽量不变，避免同时改模型、素材和流程后无法归因。再单独测试新自主流程、定向修改或素材采访。因工具能力不同导致输入不等价，应明确标注限制。

随机 A/B 身份的人工盲评，关注信息增量、结构、细节、作者声音、阅读吸引力、事实可信度。重大事实错误单独记录并阻止相应样本作为“通过案例”。不以 agent 给自己打分代替人工，不以少量样本宣称统计显著或普遍胜出。

发布门槛：所有夹具完成且结果公开到内部报告；无未处理的重大事实错误漏过门禁；人工未发现跨文体一致的明显质量退步。若大体持平但上手/恢复显著改善，可发布易用性升级，但不宣传质量提升。指标判定有主观部分，需维护者明确签收。

### 12.2 用户实验与最小指标

建议邀请 5 名目标用户，至少 4 名在不用维护者远程接管的情况下完成首篇真实任务。分别记录安装、模型接入、首稿、修改、交付各步骤阻塞，样例浏览不算真实写作激活。

再邀请有持续需求者在两周观察窗口内尝试第二篇，记录自愿返回人数与原因。这是未来实验设计，不是当前已有留存结果；样本太小不能外推总体。

默认本地记录任务指标，用户自愿导出反馈；不默认收集正文、prompt 或跨项目行为。统计必须有样本分母、观察窗口、失败和缺失项。

## 13. GitHub 与产品传播原则

当前发布实施方案见 [桌面发布手册](../launch/DESKTOP_RELEASE_RUNBOOK.md)，早期传播计划见 [历史 GITHUB_AND_LAUNCH_PLAN](../archive/2026-09-16-prd-v1.1-dsh-ui/GITHUB_AND_LAUNCH_PLAN.md)。此节的有效要求继续作为产品约束。

## 15. 风险、取舍与替代方案

| 风险 | 早期信号 | 应对 |
|---|---|---|
| 只改包名，实际仍依赖 DSH | 启动/恢复调用 dsh CLI/SDK | 独立性测试阻止合入 |
| 移植过多通用功能 | 大量无写作需求对应的插件/配置 | 按需求 ID删减范围，记录依赖闭包 |
| 为摆脱依赖而过度自研 | 重写所有网络/事件框架，无用户闭环 | 允许普通库、选择性源码复用，优先 M1 |
| 模型协议兼容性不完整 | tools/stream/usage 与预设不一致 | 能力探测与实际支持清单，不广泛承诺 |
| 数据丢失与重复操作 | 恢复后重新生成/重复提交 | 事务、版本保护、操作 ID 和 unknown_outcome |
| 事实门禁只剩 UI 标签 | 改稿后仍显示通过 | 领域事务与所有交付入口共享校验 |
| 溯源被误当成真实性 | 显示来源即可通过 | 验证支持范围与人工复核，清楚限制 |
| 上游安全问题继续带入 | 未记录来源与依赖 | 固定快照、安全评审、周期审查上游补丁 |
| 原用户被升级抛弃 | 老路径/风格/数据丢失 | Legacy 入口、只读迁移、文档与备份 |
| 文档大于实际能力 | README 宣布尚未实现功能 | 所有宣传绑定里程碑与验证记录 |
| UI 移植变成重新设计 | 新增全局 CSS、重写全部对话/侧栏 | 先通过 DSH 保真基线，仅允许明确的品牌/写作扩展 |
| 只拷组件忽视协议闭包 | 页面能显示但会话、停止、设置不可用 | 审计 client model/remote/build/host，一并移植必要代码并做契约测试 |
| 上游升级引发合并困难 | 修改散落于原组件、盲目全仓改名 | 固定 commit、集中品牌/主题层、单独上游升级 PR 与视觉测试 |

其他产品方向作为未来实验：资料优先的专业写作模式；作者记忆与风格学习；面向开发者的写作 SDK。它们共享本次领域内核，但未经独立需求验证不扩大 1.0 范围。

## 16. 待确认事项与默认处理

M0 必须查明具体 DSH 移植模块依赖、现有桌面数据 schema、包名/命令名、Node/SQLite 库选择、许可证及 CI 可用环境，并写 ADR。它们不阻止阅读和测试基线工作。

## 17. 术语速查

| 术语 | 在本项目中的含义 |
|---|---|
| Runtime 运行时 | 让 agent 真正运行、调工具、记状态、停止和恢复的代码 |
| Harness | 组织模型、工具、会话、策略和入口的外围执行系统；本产品不要求用户理解这个词 |
| Workflow 工作流 | 写作活动的大体顺序，不等同全部状态 |
| State machine 状态机 | 限制哪些状态能在什么条件下改变 |
| Agent loop | 模型提出下一步、执行工具、读取结果后再继续的循环 |
| Event 事件 | 已发生并提交的事实，如某版正文被接受 |
| Projection 投影 | 从事件/记录计算当前可展示或可判断的状态 |
| Artifact 工件 | 正文、大纲、标题、核查报告等正式产物 |
| Provenance 来源关系 | 产物从哪里来、谁改了什么、依据是什么；不是事实真实的证明 |
| Stale 失效 | 旧结果针对的输入变了，不能再作为当前通过依据 |
| Replay 重放 | 读取本地记录重新计算状态，不重新付费调用模型 |
| Recovery 恢复 | 从最后安全的持久化边界继续工作 |
| CAS/乐观并发 | 提交时检查基准版本没变，否则拒绝覆盖 |
| Idempotency 幂等 | 同一操作重复提交，不重复生成本地结果 |
| ADR | 一份短的架构决策记录：决定、原因、备选与验证 |
| 来源清单 | 记录移植代码的上游路径、commit、许可及本地改动 |
| UI shell / 前端外壳 | 页面布局、导航、输入、对话和面板的组合，不等于桌面安装容器 |
| Desktop shell / 桌面容器 | 承载同一前端、启动本地服务并交付安装包的代码 |
| Slot / 插槽 | 在已有界面的指定位置加入新面板或按钮，而不改写整个布局 |
| Design token / 设计变量 | 统一控制颜色、字号、间距等的命名值；不是每页单独调 CSS |
| Client bridge / 客户端适配层 | 把自有写作数据与命令连接到移植的前端，不在 UI 内重建后端规则 |

**实施落点：先把一个真正自主运行、可保存、可恢复、可验证的写作任务跑通，再扩展产品。原仓库积累是升级起点，不是需要被覆盖掉的旧包袱。**
