# rc.24：工具职责、调用角色与运行记录排版

日期：2026-09-22。用户反馈需求交流被显示为“其他写作工具”，无法区分 Agent 和工具；复制出的“执行段 11 次模型请求”容易误读。

## 证据与修改

只读核对用户的第 2～6 轮持久事件，工具均为 `respond_writing_intake`。旧诊断名称表仅覆盖 7 个工具，缺少该工具及作者交流等工具。其职责已在后端定义，缺的是诊断展示。

- `packages/client-bridge/src/tool-presentation.ts` 集中登记当前 24 个写作工具的中文名、用途与类别。执行契约仍以各 `ToolDefinition` 的参数、权限和实现为准，展示目录不负责授权。
- “保存需求交流”展开后显示技术名称、作用、调用者、执行结果。结果只从成功工具事件的白名单状态投影：仍在讨论、待确认方案、已保存确认结果；失败/未完成不能显示成功方案，也不透传回复正文、摘要、原始参数或任意结果。
- 新运行在 `tool.requested` 记录由请求策略提供的角色，不信任模型工具参数中的角色。需求澄清、作者交流和完整工作流均绑定自己的角色；共用工具按已记录调用者计数。
- 旧记录不补写：缺少角色时显示“未记录调用者”；明确记录为 intake 的旧运行可显示“需求澄清助手（按运行类型）”，与真实记录的角色区分。
- 未登记工具显示“未登记的工具”和安全技术名称，不继续掩盖为“其他”。自动测试检查当前源码声明的工具均有展示说明，避免新增工具遗漏。
- 执行段与统计使用真实文本分隔符：`执行段 1 ｜ 1 次模型请求 · 1 次工具调用`。复制/辅助阅读也不再粘成 11 次。
- 增加一句简短说明：Agent 负责判断与生成，工具负责读取、保存、调度；工具完成不代表整篇文章完成。主对话不新增技术字段。

协议仍为 v20，新增信息均为可选字段，旧快照有明确回退。未修改数据库结构、写作顺序、模型提示词、预算或权限，不重写旧事件。
