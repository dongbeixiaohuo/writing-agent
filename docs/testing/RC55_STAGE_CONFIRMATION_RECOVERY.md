# rc.55 — 修订、润色分别确认与版本读取冲突

## 现场与根因

2026-09-29 用户在 rc.54 共创任务中认可读者审校后，集中修订和语言终审连续保存，随后出现泛化的“门禁拒绝”。只读取原工作区事件与请求快照后确认：

1. `CO_CREATION_CHECKPOINT_STAGES` 漏了 `central_revision`、`language_review`。此前 rc.54 的真实验证在集中修订保存后主动停止，没有覆盖这两个交接点，不足以证明逐位确认完整。
2. 00:00:58（本地）的一次导演响应发出三次 `read_artifact_version`，均为 `TOOL_PERMISSION_DENIED`，触发 `TOOL_FAILURE_LOOP`。这不是事实核查拒绝，也不是模型账户额度或连接故障；“3 次”是同一响应内的三个工具调用，不能解释成三轮模型重试。
3. 恢复提示冻结了旧初稿及旧评审的必读列表。保存新阶段会令 `ready=false`，导演提示随之重新使用旧恢复信息，但权限已经绑定当前证据和润色正文。提示与实际权限冲突。

## 修改

- 共创模式：集中修订保存 → 等作者确认 → 语言润色保存 → 再等作者确认 → 标题与事实核查。自主模式不变。
- 继续复用 rc.54 上下文语义解释及版本绑定凭证，不新增“认可”口令匹配。
- 生成初稿后的导演请求统一使用当前状态；读取义务以每次更新的 `COLLABORATION_STATE.unreadArtifactVersionIds` 为准。未扩大版本读取权限，未取消事实门禁，未提高调用上限。
- 老客户端已经漏过确认点的任务，恢复时先补上最新已保存修订/润色成果的确认。重试不算认可，不重生成旧专家成果；不伪造历史上两个阶段都曾被确认。
- 确认问题直接放在成果末尾。主对话展示具体版本权限冲突，运行记录保留原始错误码；历史失败的解释绑定该事件，不被后续等待覆盖。

- 逐阶段确认测试先失败于预期 `central_revision`、实际没有该等待。
- 恢复指令测试先失败于旧正文 ID 仍出现在当前请求。
- 老版本恢复测试先错误进入标题等待，而非润色确认；修复后均通过。
- Runtime **272**、Migration **15**、Conversation **67**、Legacy parity **59**、UI **79**、Bridge **64**、Desktop **44** 通过。Runtime 最终以文件串行执行，避免毫秒级传输测试受并行构建负载影响。首次并行执行有一个 60ms 级传输计时测试失败，单独重跑和最终完整串行运行均通过，未改运输超时实现或放宽测试阈值。
- 更新旧测试假定：原来连续执行的两个专家现在各需一次确认；恢复读取仍只针对绑定版本。
- 补跑事实来源边界 4 项通过；以上合计 **604 项**。Runtime/Web/Desktop TypeScript 检查及桌面分发边界检查通过。

真实 MiniMax-M3.1-Flash-Preview 使用 SQLite 在线备份，共 **11 次请求**：

1. 恢复旧 `TOOL_FAILURE_LOOP` → `language_review` 确认等待。
2. 输入“这一版可以，往下继续” → 持久语义确认 → 标题候选保存并等待作者选择。
3. 无新增工具失败，所有既有正文版本保持不变；没有调用内容主笔、语言润色或事实核查专家重新生成，也没有代选标题、放行事实核查。
4. 原项目仅只读访问，写入只发生于独立 TEMP 副本。
