# RC59：需求对话工具格式恢复

## 现场证据与根因

- 2026-10-02 12:11:58–12:14:33（上海时间），用户选中已展示的标题后，`zhipu-coding-anthropic / glm-5.3-flash` 的需求对话失败。
- 第一请求有持续流内容，约 98 秒后结束；`respond_writing_intake` 缺少顶层 `summary`，却在 `proposal` 内返回了该字段，被 schema 正确拒绝。
- 第二请求是程序触发的格式纠正，有持续流内容，约 57 秒后结束；完整响应终态到达，但工具参数无法通过 `JSON.parse`。
- 当时日志没有保存无效参数原文，因此不能断言第二次具体是哪个字符错误，也不能归因为网络超时或输出 token 耗尽。
- 程序遗漏：schema 错误携带 `toolSchemaFeedback`，能进入有限纠正；JSON 语法错误只返回通用错误码，不能进入该路径，直接终止整轮。这不是用户选题措辞不匹配。

## 修复边界

1. 收到完整响应终态后，JSON 参数语法错误也返回脱敏、可操作的格式反馈。
2. 与 schema 错误共享原有的每专家上下文最多两次纠正额度，不增加全局预算。纠正时直接要求工具提交，避免额外重复公开长回复。
3. 不拼接残缺 JSON、不自动补齐授权、不吞掉未知字段、不绕过 schema、权限或业务门禁。失败批次不会执行任何工具；断流/未知外部结果仍沿用原有恢复规则。
4. 在需求工具 schema 和模型指令中明确 `summary` 的顶层位置，避免与 `proposal.brief` 混淆；用户仍自然对话，无需了解参数格式。
