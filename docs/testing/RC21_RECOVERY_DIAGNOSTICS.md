# rc.21 恢复重复读取与运行详情

日期：2026-09-22。用户提供 rc.19 执行详情，反映意外阻断和大量无信息量的“读取参考材料 · 已完成”。本轮修复沿用 rc.20，整体 `BLOCKED_CORE_WORKFLOW` / WA-010 `IN_PROGRESS` 不变。

## 现场证据与根因

原工作区仅通过 `DatabaseSync(..., {readOnly:true})` 查询。目标 run：`018ef7ec-f79e-47c6-937a-29d1e40efc0c`；开始 2026-09-21 23:52:37、结束 2026-09-22 00:28:31（北京时间），状态 `budget_exhausted`。

- 33 次模型请求、96 次工具调用；其中材料读取 67 次（66 成功、1 次权限拒绝）。15 份材料在开始与研究各读一遍，提纲确认及初稿确认后又各读一遍，最后恢复只读到第 6 份就触及原有 96 次工具保护阈值。
- 4 次 `DIRECTOR_UNRESOLVED_QUESTIONS`：模型把给专家的评审问题或“（暂留）”“（无）”放入用户问题数组，错误反馈仅说先解决问题，未明确空数组写法与任务说明的区别。
- 发布审校请求 `f46c1484-7ea2-491a-b6cb-a16b77c8945f` 为 `request.outcome_unknown / TIMEOUT`。用户显式选择 `retry_unknown` 后，程序丢掉当前执行段之前的专家分派，又进入导演调度、重新读材料，最终触发保护。此处外部超时本身不能以此次本地修复宣称消除。
- 材料“已读”只计算最近 `run.resumed` 之后的事件；但专家上下文又注入整个 run 的历史材料读结果，恢复时已累计 60 份重复片段。工程约束与模型实际获得的材料状态矛盾。
- Runtime 同一 actor scope 内只在首次组装 system/user 消息，后续工具执行后的 `ready/materials` 状态没有刷新。专家能看见工具结果但仍收到旧状态。
- rc.19 运行详情复用主 Timeline 的合并投影，模型调用被合并、工具结果只剩泛化标签，既难解释失败也不能可靠逐次追踪。

## 修复范围

1. 同一个 run 内已完整读取的授权材料按 materialId + 当前 contentVersionId + 连续范围复用，不因用户确认而失效。变化版本、未读/缺失片段仍不满足门禁；不是跨 run 通用缓存。每个独立专家获得当前授权版本的去重材料数据，不共享其他专家私有会话或初审意见。
2. 同 scope 更新权威 system/user 状态，同时保留当前 actor 自己的工具历史；换角色仍建立隔离上下文。提示词明确区分“需要重新评估用户反馈”和“需要重新读材料”。
3. 仅无新增用户修改指令的显式 `retry_unknown` 保留未完成专家分派；先评估恢复上下文，再接回原任务。真正用户反馈仍交由导演重新决策；恢复必读稿件、版本 CAS、独立评审与事实门禁不放宽。
4. 导演工具 schema / 纠错反馈明确：派发、返工、结束使用 `questions=[]`，专家任务问题写入 reason，真正需要用户回答则 `action=ask`。没有静默丢弃问题、自动代答或自动确认。
5. 运行详情独立投影持久事件：按开始/恢复分段，保留每次模型请求（耗时为事件时间差、用量缺失保持未知、错误 code）、导演任务摘要/展开全文、按材料与版本汇总的次数和失败 code。主对话仍不展示技术调用。
6. 长任务与逐请求列表默认折叠；专家使用中文角色名并保留阶段技术标识。材料先显示精简名称/状态/短版本，完整标识展开查看。禁止透传原始模型请求、工具正文、凭据及源路径。历史记录只改展示，不删除或改写实际次数/失败状态。
