# rc.50：输出上限兜底升 32768、提纲去内部编号、设置页反馈补强

日期：2026-09-27。范围：三个模型适配器的默认输出上限、提纲阶段指令、设置页模型目录交互；不修改写作工作流门禁、事实核查口径、存量项目数据或凭据。网络搜索按用户决定继续推后。

## 根因与证据（用户报告三项）

1. **输出仍被截断**：rc.49 修了"thinking 烧预算"和"同预算重试"，但三个适配器的兜底输出上限仍是 4096（Chat 适配器甚至省略 `max_tokens`，把决定权交给服务端默认）。FDE 项目标题确认后继续核查时再次截断。用户原话："默认输出设置的是有多低啊？现在模型都是1M了，再省什么？"
2. **提纲出现 E003 这类编号**：研究阶段的证据编号（E001/E002…）是给程序账本用的内部标识，提纲是写给作者看的确认稿，出现编号莫名其妙。根因是提纲阶段指令没有禁止把账本字段带进提纲。
3. **设置页三处无反馈**：点"保存并验证连接"没反应（按钮在检查已保存 Key 期间被禁用但无任何说明，忙碌时只显示"处理中…"）；点"获取可用模型"后结果只藏在 datalist 里，输入框不显示任何模型；保存成功没有明确的成功提示。

## 修改

1. **默认输出上限 4096→32768**：`openai-compatible` 新增导出常量 `DEFAULT_MAX_OUTPUT_TOKENS = 32768`，`serializeRequest` 不再省略 `max_tokens`（用户未设置时显式发送 32768）；`openai-responses` 的 `max_output_tokens`、anthropic 适配器的 `outputTokenLimit` 兜底同改为该常量。用户显式配置与 MiniMax M3 专用值 131072 不受影响；rc.49 的截断恢复 ×2（封顶 65536）逻辑不变。
2. **提纲禁止内部编号**（`packages/application/src/collaboration.ts`）：提纲阶段指令明确——提纲是给作者的确认稿，禁止出现 E001/E002 这类证据编号和 use_boundary、illustrative 等内部字段名；证据与观点的对应关系由研究账本承担（草稿阶段经绑定 artifact 取账本，不靠提纲里的编号）；需要说明来源性质时用自然语言。
3. **设置页反馈补强**（`packages/ui/src/shell/ProviderSettings.tsx` + CSS）：
   - "获取可用模型"成功后：当前模型行为空时自动填入目录第一项，并把目录前 8 个渲染成可见可点的模型标签（点击填入当前选中行）；datalist 保留；返回空列表时有明确提示。
   - "保存并验证连接"：忙碌时文案改为"正在保存并验证连接…"；因正在检查已保存 Key 而禁用时，按钮旁给出可见说明（"完成后才能保存；输入新 Key 可立即保存"）。
   - 保存成功且验证通过：提示"已保存并验证通过：{model} 已可用。已有项目下次继续时生效。"；验证未通过保持编辑器已关闭+错误横幅（带 rc.44 上游原因），提示语如实区分"已保存"与"验证未通过"。
4. **陈旧断言随 rc.47 口径修正**（`packages/writing-pack/test/expert-instructions.test.ts`）：两处事实核查断言仍按 rc.47 之前的"逐字审计"口径书写（`用户.*原话.*主观感受.*外部证明`、`完整最终正文`），rc.47 把核查范围重定为"可被外部世界证伪的事实主张"后一直红，本次改为钉住现行口径（外部证伪对象、第一人称亲历属作者表达权、用词一致类不生成 C 编号）。
