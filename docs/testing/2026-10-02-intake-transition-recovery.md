# RC59 需求确认循环：取证与回归

## 现场与根因

2026-10-02 本机 RC59：作者补充“1500字，其他没问题”，随后回复“ok”，助手仍反复要求确认。

只读核对该项目的持久事件，四次 `respond_writing_intake` 都只提交了 `reply`、`summary`、`questions`，没有 `proposal` / `confirmation`。模型在文字里说“已提交暂定方案”，实际未存储方案。运行成功仅表示聊天保存成功，状态仍是 `collecting`。旧实现仅在 `proposal` 阶段解释确认意图，因而永远无法进入确认分支。不是网络问题，也不是作者使用了错误的确认口令。

RC59 的格式恢复测试只证明回复可以保存，没有覆盖“已讨论方向 → 真实方案 → 自然认可 → 写作交接”。这项验收缺口由此次回归补齐。

## 修复边界

- 有历史交流但仍在收集阶段时，也通过模型结合完整对话判断是否可以形成方案，不匹配作者口令。
- 语义决定 `propose_direction` 后，仅开放专用 `submit_writing_proposal`。方案字段为必填，不能把只保存聊天当作提交方案成功。
- 专用工具只传写作偏好、建议项及可选的来源绑定授权，摘要由程序排版；不要求模型再把长回复包进多层 JSON。
- 对已有方案的 `confirm_direction`，程序绑定当前持久版本落实确认；生成回复时漏传确认字段、重复提案，都不能让原方案继续停在待确认。显式错误版本和来源仍拒绝。
- 不新增亲历、模仿风格或自主推进授权。普通口吻/情绪是写作偏好，不应被填成特殊风格授权。
- 自动纠正仍有边界；失败不能伪装为“交流已保存、请再确认”。原材料和已有成果保留。

## 验证

新增失败优先测试覆盖：漏方案纠正、只保存聊天不能假成功、语义认可后漏确认字段、认可后模型擅自重新提案、仅讨论不授权、持续错误有界停止。

桌面桥接回归覆盖：历史聊天补存可见方案，自然认可后在同一对话真正启动写作，并停在共创检查点。

真实重放脚本：`tests/ux/intake-transition-replay.ts`。源数据库只读，所有写入在独立临时工作区；用当前实际配置模型，经桌面桥接重放“1500字，其他没问题 → ok”，验收必须检查方案状态、写作启动和首个共创检查点，不能只检查请求成功。

历史缺失方案的项目无需新建：下一轮会先补存可核对的方案，再对该真实版本确认一次。不能把从未持久化的方案直接标记为已确认，也不会修改原项目历史记录。
