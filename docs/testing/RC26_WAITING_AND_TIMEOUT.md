# rc.26：真实等待反馈与分阶段超时

日期：2026-09-22。授权范围：普通用户在等待期间始终有可理解反馈；持续输出不再被整次请求 60 秒限制打断。保留专家隔离、持久化校验、取消及原项目恢复规则。

## 修改

- 主对话只增加一条状态区，随真实请求角色和响应事件更新，不刷工具日志、不模拟思考、不显示虚构百分比。发送中的即时状态和输入焦点保留，进入运行后显示本次请求用时、可见的“停止”按钮。
- 区分等待响应、已收到响应头但尚无有效内容、已开始接收内容、接收后长时间没有新内容。导演显示核对/安排，研究、提纲、正文和审校显示对应职责；未知角色使用安全通用名称。内部文本和工具参数仍不展示。
- OpenAI-compatible 与 Anthropic-compatible 共同改用分阶段时限：首次有效内容默认 180 秒，之后连续无有效内容默认 90 秒。持续有效内容重置停滞计时，没有原来的 60 秒总时限；响应头、心跳、空事件、用量信息不能无限延长等待。
- Anthropic thinking 增量只记录“有有效活动”，不透传原文。模型输出的正文/提纲等已允许字段仍实时显示，未完整校验保存的片段不是正式成果。
- 取消和提前停止迭代会释放计时器、信号监听及连接。未自动重试超时请求，不增加预算，不修改用户模型配置。
- 中断提示区分首次响应等待超时和中途停滞，明确是客户端停止等待；不再统一称为“连接问题”。历史记录缺少证据时保持通用说明，不推断不存在的数据。
- 运行记录新增响应头、首次有效内容、最后有效内容时间，以及客户端时限阶段；另保留服务商 HTTP 状态。只投影固定字段，不保存私有流片段或凭据。协议仍为 v20，新增快照字段可选，无数据库迁移。

## 归因更正

本轮进一步核对发现，旧 runtime 的 `failureFromModel` 会把持久错误缩减为 code/message/retryable。因此旧日志没有 HTTP status，不能单凭这一点排除 HTTP 408，也不能严格证明某次 60 秒超时一定由客户端触发。代码中的 60 秒整次截止是已确认缺陷，最近请求约 60 秒中断与该缺陷相符，但历史来源证据不足。Windows 睡眠事件仍足以证明 3037.9 秒不是连续服务商处理耗时。

新版本明确记录客户端 transport 原因与 providerHttpStatus，避免继续混淆两类问题。此前 rc.25 文档的确定性归因以本补充为准。
