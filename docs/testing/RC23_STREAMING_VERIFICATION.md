# rc.23：主对话真实增量与等待反馈

日期：2026-09-22。范围为用户反馈的 rc.22 长时间无文字、随后整段出现。不改变已确认材料、专家隔离、事实门禁或恢复授权。

## 现场与根因

- rc.22 只把特定工具参数内的 `reply/content` 投影为预览，忽略了正常的 `text_delta`。此前本地工具片段测试通过，不足以证明真实模型的普通文本也能显示。
- 独立空工作区、原 rc.22 打包应用真实请求复现：`output/rc23-real-streaming/rc23-24fa9a59754c4c589ff23d4f9b3909cd/result.json`，540 字普通回复约 15.6 秒后才整体可见。
- 初版修复实测：第一轮普通文本持续增加，第二轮工具回复仍集中出现，严格测试判 FAIL；保留证据 `rc23-0a89f18e36b64d50a5d2320735e586d6`，未交付该中间包。
- 独立工具请求探针 `provider-probe-1790050611062.json`：首个非空工具片段约 9.088 秒，后两个片段约 9.133 秒。说明兼容端点可能集中发送工具参数；客户端不能显示尚未收到的文字。

## 修复与边界

1. Runtime 请求策略增加内存态 `textAudience: conversation`。需求交流和作者交流的导演可展示普通文本；未显式授权的内部专家文本默认隐藏。原有允许展示的工具字段继续按增量解析，研究 JSON、工具原始参数不直接展示。
2. 需求交流不再强制 `toolChoice=required`，改为 `auto`，要求公开回复先用普通文本输出，再用工具保存同一内容。即使模型不调用保存工具，工程层仍拒绝将这轮视为完成，并在原有保护范围内要求补齐保存；不是靠提示词认定已保存或授权。
3. 已显示的普通回复不会因同一回复开始写入工具参数而退回半句话。预览仍与已保存内容分开；取消、错误、重试和请求切换清除临时内容，不把半截回复提交为稿件。
4. 首个片段之前显示“已收到，正在处理你的消息；有新回复会直接显示在这里…”，并纳入主对话跟随定位。不是模拟进度或收到全文后的打字动画。

限制：`auto` 不保证供应商一定先发普通文本。工具分支也按真实片段立即显示；上游集中返回时仍可能几段快速出现。首字延迟、网络和模型自身思考时间未被消除；不承诺所有模型逐字输出或秒回。
