# rc.47：标题选择口语识别、DeepSeek 双协议修复、事实核查正位、对话 minimap、确认收敛

日期：2026-09-27。范围：标题选择解析、DeepSeek 请求适配补全、事实核查职责与联网能力、对话导航交互、暂停提问展示；不修改事实门禁、存量项目数据或凭据。

## 根因与证据（用户报告五项）

1. **说了"选择标题2"却被反复要求确认**：`publicationSelectionIndex` 的正则只认"动词+第+数字"语序（选用第2个），不认"选择标题2/确认标题2/用标题二"这种"动词+标题+数字"的自然说法，量词表还缺"条"——连界面建议用户回复的"用第2条"都解析不了。于是系统按"未明确选定"处理，模型只能反复追问。
2. **DeepSeek 仍报 thinking 错**：rc.45 的 thinking-disabled 只覆盖 Chat 协议配置与 Chat 适配器，用户实际保存的是 **Responses 协议**配置且未做手动切换，`/responses` 请求体仍不带 thinking 开关，继续被拒。
3. **事实核查在咬文嚼字**：核查专家把第一人称亲历叙述的合理加工（"附和OK的那几位表情如常"）、语感润色（"互相客套两句"）、用词统一建议（"董事成员/董事会成员"）都列为 C 编号问题项，而没有聚焦"外部可证伪事实"这一真正职责；纯个人感受文章被这些 bureaucratic 项阻断。
4. **长对话只能拖滚动条**：参考 Codex 侧栏小横线设计，用户要的是对话位置 minimap（rc.46 误做成了悬停预览，非用户所需，已撤除）。
5. **"这不是废话吗"式确认**：暂停卡片把同一问题在 reason 段落和编号列表里展示两遍；且"核查范围按……正文不动，可以吗"属于程序应自动确定的程序性确认，不该问用户。

## 修改

1. **选择口语识别**：解析器新增"动词+标题+数字"（选择标题2/确认标题2/用标题二）、"标题2/标题第2条"独立形式，量词表补"条"（用第2条/选第2条/就用第2条/第2条），确认形式补"确认标题：《X》/确认《X》"。14 组正例 + 4 组反例测试钉住，不误判"说说标题2的问题"。
2. **DeepSeek 双协议修复**：openai-responses 适配器同样消费 `extraBody`（wireBody 合并，快照一致）；`withPresetExtraBody` 匹配放宽为"供应商 ID + 端点"（DeepSeek 的 thinking 拒绝发生在两个协议上，属端点级语义）；`createConfiguredProvider` 的 Responses 分支透传。**用户现存 Responses 配置在读取时自动获得 thinking-disabled，无需任何手动操作。** DeepSeek Responses 端点兼容性仍属未账号验证边界，若其流式事件与严格校验不符，失败会带明确上游原因，Chat 仍是已验证备选。
3. **事实核查正位**：专家指令重写——核查对象只有"可被外部世界证伪的事实主张"（数字/日期/人名/机构/政策/报告/引语/新闻事件/链接/历史或科学论断/被当作真实的第三人称事件）；第一人称亲历叙事属作者本人的来源，合理加工、细节补写、语感润色不再判超范围；用词一致与文风对齐归语言终审，不生成 C 编号；无外部事实主张时直接空 claims 通过。新增 `read_fact_source` 工具：核查专家可**联网重读证据账本中已登记的来源 URL** 核对引用（复用 NetworkAccessPolicy + SecureWebFetcher 的安全链路，只读不落盘、URL 必须在账本逐字出现，否则标 NEEDS_USER_SOURCE，禁自由浏览）。draft run 授予 `network:https:read`（仅此工具消费）。
4. **对话 minimap**：会话流右缘新增定位条——每条消息一个小横标（位置/高度按全文比例）、当前视口高亮框、点击跳转平滑滚动；仅当内容可滚动时出现；rc.46 的悬停预览按用户澄清撤除（状态、事件、卡片、CSS 全撤）。
5. **确认收敛**：暂停卡片对"问题已写进 reason"的情况做精确去重（归一化后子串判定，宁缺勿滥，不同问题一定显示）；导演提示词新增禁令——核查范围、阶段顺序、是否继续等程序性问题一律不问，reason 不复述问题（只写为什么需要补充），提问仅限真实业务缺口。
