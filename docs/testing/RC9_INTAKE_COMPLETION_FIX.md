日期：2026-09-20。候选版本 `1.0.0-rc.9`，协议 v19。此次是定向缺陷修复，不改变整体 `BLOCKED_CORE_WORKFLOW` 和 WA-010 `IN_PROGRESS`。

## 当前现场和根因

用户报告 rc.8 正常对话出现“运行预算已用完，请缩小任务范围后重试”。只读检查用户当前 SQLite 中对应运行，未改数据、未访问 API Key，未再次调用真实服务商。

- 运行 `e0222b68-fb57-4b99-be92-eb35f76dcf1e`，本地时间 2026-09-20 15:58:09–15:58:34，purpose 为 `writing-pack:intake`。
- 内置单轮保护为 4 次模型请求、2 次工具调用、每请求 1 次重试、0 次重大修订。不是用户配置的费用预算，也不是服务商配额告警。
- 模型先返回三次未通过持久化工具提交的文本；第 4 次请求调用 `respond_writing_intake`，工具成功保存了自然语言回复。随后 runtime 为通用工具循环准备第 5 次模型收尾，派发前被保护拦住。
- 持久事件顺序：`request.completed` → `tool.completed`（成功）→ `request.prepared` → `run.budget_exhausted`。实际已派发 4 次模型请求、1 次工具调用、0 重试。未把费用未知解释为零费用。
- 因此属于成功结果判定与循环收尾错误，不能靠提高上限或要求用户缩小主题解决。

## 修复边界

1. 应用层明确声明澄清工具的成功持久结果为终态，runtime 在记录 `tool.completed` 后正常完成，不再请求模型收尾，也不执行同批后续响应工具。此策略只在澄清业务启用，其他写作工具循环默认不变。
2. 澄清请求明确使用 `toolChoice: required`，要求模型通过响应工具保存回复；供应商仍不遵循契约时，保留有界纠正与安全停止。
3. 原取消、版本绑定、输入校验和用户授权不被放宽。未成功保存回复不能冒充成功。
4. 主对话和运行记录将内部限制称为“运行保护”，明确不是服务商账户额度。历史失败若已有保存回复，提示可以直接继续对话；若未保存，明确本轮回复未保存而用户消息仍保留。
5. 旧失败审计不篡改为成功；每次新用户答复独立计数，不是对话总轮数配额。没有新增费用上限、费用设置或放大既有调用上限。
