# 原仓库演进、发布与传播方案

文档版本：1.1 · 2026-09-16。所有仓库设置、Issue 和 Release 操作均为后续计划，本包未执行远程写入。

## 1. 仓库策略

唯一产品主仓库继续使用 `dongbeixiaohuo/writing-agent`。不创建第二个面向用户的主仓库，不把旧仓库标归档，不删除 `.git`，不使用 orphan branch/强推覆盖历史。

DSH 可作为只读上游参考 remote 或工作区外的固定快照。将需要的源码及依赖闭包通过正常提交加入原仓库，记录来源；不把本仓库替换为 DSH 的完整 git 历史。不需要在 GitHub fork network 中改变原项目身份。

架构重做不意味着仓库身份重做。同一仓库不需要把 star 从旧分支“搬到”新分支；它仍属于同一仓库。保留 star 不是永久保值承诺，用户仍可以取消收藏。[S01][S11]

### 分支结构

```text
main                      旧稳定入口，直到 1.0 验收通过
 └─ next/runtime          新运行时集成分支
      ├─ feat/runtime-storage
      ├─ feat/runtime-loop
      ├─ feat/dsh-ui-port
      ├─ feat/writing-ui-panels
      ├─ feat/writing-revision
      ├─ feat/fact-gate
      └─ feat/legacy-import

legacy/0.x                仅在主线切换前从最后认可的旧版 commit 建立
```

功能分支小 PR 合到 next/runtime。main 上必要安全/缺陷修复通过正常 PR，并及时合入 next/runtime；避免长期两条分支完全失联。文档 RFC 和预览入口可以提前以小 PR 放到 main，但不能破坏旧安装指引。

不固定一个不存在的旧版 tag。M0 先检查 tags/releases 与实际 commit；有历史 tag 就使用，没有则维护者审核后创建新的明确 legacy tag，不覆盖现有名称。

### 旧版支持范围

旧分支只保留关键缺陷、安全修复和迁移说明，不承诺同步全部 1.0 新能力。原插件安装路径继续可发现。主线切换前，完整旧文档可存于固定 tag 和 `docs/legacy/` 指引；不把历史源文件挪走后使旧引用全部失效。

旧桌面 0.1.0 保留历史发行与迁移入口，不再扩展为新版 UI。新旧安装包用明确通道与独立应用数据目录区分，不用“自动升级界面”掩盖迁移。

不并行维护两套不断演化的同名写作规则。旧 `claude-runtime` 镜像保持原同步体系；新 writing-pack 的来源和差异显式记录，迁移结束后文档明确哪个运行模式使用哪个版本。

## 2. GitHub 项目管理

建议按里程碑设置 M0–M4，标签先控制数量：`runtime`、`writing-core`、`migration`、`security`、`ux`、`docs`、`evaluation`、`bug`、`good-first-issue`、`help-wanted`。

`WA-001` 等是本地计划 ID，不是已创建的 GitHub Issue 编号。实际创建后在任务清单增加 `github_issue_url`，避免把数字相同误认为同一任务。

### 首个总跟踪 Issue 草案

**标题：** `[RFC] Writing Agent 1.0：从写作工作流升级为独立运行时`

**正文：**

```markdown
## 为什么改造
现有项目已经积累了写作规则、证据和核查流程。下一阶段将降低宿主与部署依赖，
使稿件、修改、作者决定和执行过程成为可恢复、可验证的产品能力。

## 技术方向
参考并选择性移植 DeepSeek Harness 源码，在本仓库内独立维护运行时。
新版不作为 DSH 插件，不要求用户安装 DSH 或 Claude Code。
复用代码保留来源和许可证，写作领域模型由 Writing Agent 定义。
前端直接复用 DSH 的页面、布局、主题及必要源码，先保留其界面体系，再增加写作面板；
不利旧 0.1.0 桌面 UI，不把新产品变成连接 DSH 服务的客户端。

## 不变的部分
原仓库、旧版入口、历史文章、写作方法和用户资产保留。
旧稿导入不自动继承新版核查通过状态。

## 里程碑
- [ ] M0：基线、许可证与移植设计
- [ ] M1：自有循环/恢复，与 DSH 前端源码基线并行推进
- [ ] M2：DSH 派生 UI 接真实写作服务、局部修改、事实门禁与视觉验收
- [ ] M3：旧数据迁移与独立安装包
- [ ] M4：评估、文档与 1.0 发布

## 当前状态
此 RFC 是路线规划，不代表上述功能均已实现。可运行版本以 Release 说明为准。

## 反馈重点
请描述一项你真实完成过或希望完成的写作任务，以及目前卡住的步骤。
不要提交 API Key、私人文章全文或未经授权的第三方资料。
```

发布 RFC 属于对外行为，开发 Agent 先准备草案，维护者确认后创建。可以置顶该跟踪 Issue。当前仓库未启用 Discussions；可由维护者开启后使用 Announcements / Feedback 两类，否则继续用 Issue，不把启用 Discussions 作为开发前置条件。[S01]

## 3. PR 与 CI 规划

PR 类型至少区分：上游源码引入、行为适配、写作领域实现、数据迁移、依赖升级、文档/发布。源码移植 PR 尽量分成“保留来源的初次导入”和“有测试的本地适配”，让审查者看清原始与修改边界。

每个 PR 描述：相关需求/任务、文件范围、上游来源、用户可见变化、schema 变化、测试及未测试项、回退方式。不可用全仓格式化掩盖逻辑变更。

建议 CI 分组：

| Job | 作用 |
|---|---|
| legacy-check | 原 Python/工作流/同步/插件回归；所需旧宿主只存在于此测试环境 |
| runtime-check | 类型、单测、mock 模型循环、事件重放 |
| writing-contract-check | 版本、锁定、冲突、事实 gate 和 TS/Python 差分 |
| ui-origin-check | DSH 固定源映射、资产许可、无旧 UI/启动链依赖、独立品牌/端点 |
| ui-contract-check | Client bridge、项目切换、重连/取消、Slot 注册与协议版本 |
| ui-visual-check | 固定夹具的上游/派生页面对照、主题、布局、键盘/滚动与差异白名单 |
| security-check | 越权、网络策略、HTML、安全依赖与 secret 扫描 |
| migration-check | 原目录和桌面数据导入、重试、备份与回退 |
| package-check | 安装包内容、无外部宿主依赖、第三方声明及哈希 |
| integration-check | Windows 自包含启动与核心用户旅程 |

初期按任务逐步启用，不建立一堆永远 SKIP 的“绿灯”。真实模型测试单独、显式授权、限预算执行，不在每个外部 PR 自动消耗维护者密钥。

## 4. 版本和发布通道

建议新系统采用同一产品版本序列：`1.0.0-alpha.N`、`1.0.0-beta.N`、`1.0.0-rc.N`、`1.0.0`。若原 tag 冲突，可使用 `runtime-v1.0.0-alpha.1` 等具名 tag；不要移动旧 tag。旧插件版本按其实际维护版本保留，不伪称已经切换 runtime。

GitHub 预览版本标为 prerelease，包含对应目标 commit、支持系统、安装要求、已验证能力、已知限制和回退方式。正式版本明确选取正确 latest，旧版仍可检索。[S12]

npm 通道仅在包名归属与权限核验后建立。目标可用 `next` 对应预览、`latest` 对应稳定，但未发布前 README 不展示貌似可用的安装命令。独立分发与 npm 发布不是同一件事，可先发 GitHub Windows 包。

### 每次 Release 最低内容

- 精确 tag/commit、操作系统/架构、包版本、模型测试范围。
- 真实安装方式与环境前提，不混淆源代码安装和普通用户安装。
- 更新内容及其验收记录，不把计划功能写成已上线。
- 已知问题、隐私/网络说明、旧数据备份/迁移/回退。
- 安装资产、校验和、适用许可证/第三方声明、签名状态。
- 小而完整的示例，含脱敏材料、稿件、改动、核查状态和复现说明。

## 6. 三次传播节点，不只换一张截图

### 节点 A：Alpha，证明引擎真的属于自己

演示：DSH 派生界面从本地独立启动 → 自有运行时调用材料工具 → 产生稿件版本 → 查看事件 → 退出并恢复。

可以更早展示 UI 移植进度，但必须标明是本地 mock 还是实际连接；“界面移植预览”和“独立写作 Alpha”不能混为一条已完成公告。展示品牌变化、来源 commit 和必要裁剪，不暗示全部界面原创。

受众：原项目贡献者、对 runtime 开发感兴趣的人。内容重点是源码移植边界与可复現工程闭环，不冒充面向所有作者的成熟应用。

建议文章标题：`Writing Agent 为什么开始拥有自己的运行时`。正文附上来源声明、已实现清单、未做清单与复现方法。

### 节点 B：Beta，证明修改可控

在保留 DSH 界面基础的同一工作台中，演示锁定段落、局部修改、冲突拒绝、版本差异、正文变化使核查失效。展示新写作面板，而非再做一套无关首页。使用可公开材料或合成夹具，不上传私人客户内容。

受众：有文章任务的原用户。邀请自愿提交任务与反馈，不要求先 star 才能参与，不批量联系所有收藏者。

### 节点 C：1.0，证明普通用户能完成任务

演示干净环境安装、首次模型接入、完整写作与交付，以及旧项目导入。公开测试与限制，说明质量评估到底支持什么结论。

发布内容必须有已存在、经过验收的下载入口。若 Windows 签名或模型接入仍有要求，开头就说明，不藏在 FAQ 最后一段。

## 7. 利用原项目资产

| 原有资产 | 使用方法 | 避免的误用 |
|---|---|---|
| star 和仓库链接 | 保留单一入口，公开升级进展 | 以为每个 star 都能收到通知 |
| 原 Issues | 分类“安装/使用/质量/模型”，回到真实问题验证 | 把已关闭旧反馈说成当前已证实 bug |
| 原 Demo | 保留历史样本并新增 1.0 对照/恢复示例 | 修改旧结果后伪装过去已有能力 |
| 旧桌面预览版 | 明确 Legacy 身份、提供数据导入演示，说明新 UI 来源 | 将旧用户保留误写为旧 UI 继续演进 |
| 写作方法和契约 | 解释哪些规则进入 runtime，以及有何测试 | 宣称以前只有提示词所以没有价值 |
| 评测工具 | 发布可复现材料与描述性结果 | 用小样本排名证明普遍最好 |
| 已有文章/社区渠道 | 在维护者实际拥有的渠道发布真实体验变化 | 假定已连通公众号、自动群发或虚构媒体合作 |
| 贡献者与 fork | 在相关讨论中感谢实际贡献，给清晰迁移/贡献任务 | 全员 @、复制私人邮箱做营销 |

当前可确认的仓库快照为 417 stars 和 4 个 Watch 订阅者，Watch 也不等于完整潜在触达人数。通知受用户设置影响。不要以 API 的 `watchers_count=417` 错把收藏者当订阅者。[S01][S11]

### 界面协作的传播入口

当内部主题/Slot 扩展示例可运行后，在原仓库提供一篇 UI_EXTENSION_GUIDE，展示改品牌、改主题、加写作侧栏的最小差异。把经许可、经审核的改进通过小 PR 汇集在原项目，而不是再建一个 UI 分叉主仓库。欢迎贡献主题/文案/可访问性或组件测试，不以线上插件市场作为前置条件。

用户提出某个社区魔改界面时，先取得具体源码/页面、核对许可与相对基线，再决定选择性移植；不默认拥有全部社区 UI 的复用权。

## 8. 指标与反馈闭环

技术指标：安装成功、运行完成/停止原因、恢复成功、版本冲突保护、核查失效保护。质量指标：人工盲评和重大事实错误。产品指标：真实首篇、定向修改完成、第二篇自愿返回。传播指标：Release 访问/下载、有效反馈、新贡献者和 star 变化。

前三类决定是否值得继续迭代，star 是辅助信号。下载次数不等于唯一安装人数，star 不等于使用者，公开 GitHub 数据不能给出产品留存。

建议按发布观察窗口建立本地/文档表：时间、版本、来源渠道、访问/下载（可获得时）、试用人数、自愿完成任务数、阻塞类型、反馈处理状态。缺失记 unknown，不按 0。

文章与遥测默认不自动上传。邀请用户提供脱敏诊断、任务简报和明确授权的稿件，必须允许只反馈问题而不交全文。
